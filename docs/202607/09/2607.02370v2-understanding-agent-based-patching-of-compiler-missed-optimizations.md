## 摘要
编译器遗漏优化是指编译器未能对某些代码进行优化的情况。实现或修复此类遗漏优化通常需要众多编译器开发者投入大量工作。本文系统研究了智能体在修复编译器遗漏优化方面的表现。我们发现，一个重要挑战在于，修复遗漏优化不仅仅是修复报告中的特定案例，还需要将优化推广到相似情况。我们构建了一个基于真实世界 LLVM 遗漏优化问题的基准数据集，并从优化覆盖范围的角度，将智能体生成的补丁与开发者提交的补丁进行了比较。结果表明，代码智能体通常能够优化给定示例，但许多生成的补丁仅覆盖开发者预期范围的一部分，或与其部分重叠；在某些情况下，它们甚至比参考补丁进行了更进一步的泛化。我们进一步提出了历史知识增强技术，通过检索与蒸馏利用以往 LLVM 优化拉取请求中的信息，结果表明该方法能够提升与开发者一致的泛化能力，并在应用于真实世界 IR 时带来实际收益。

## Abstract
Compiler missed optimizations refer to cases in which compilers failed to optimize certain code. It takes many compiler developers' efforts to implement or patch such missed optimizations. In this paper, we present a systematic study of how well agents patch compiler missed optimizations. We identify a significant challenge that patching a missed optimization requires more than just fixing the reported case, and instead requires generalizing to similar cases. We construct a benchmark of real-world LLVM missed optimization issues and compare agent-generated patches with patches from developers in terms of optimization scope. Our results show that coding agents often optimize the given examples, but many generated patches either cover only part of the developer-intended scope or partially overlap with it; in some cases, they further generalize beyond the reference patch. We further introduce historical-knowledge augmentation techniques that leverage prior LLVM optimization pull requests through retrieval and distillation, showing that they improve developer-aligned generalization and yield practical benefits when applied to real-world IR.

## 1. 核心问题与整体含义

### 研究背景

现代编译器（如 LLVM）依赖大量优化规则来识别和替换低效代码模式，但现实中经常会出现“遗漏优化（missed optimization）”问题，即：

- 编译器没有发现某种本应可以优化的 IR（Intermediate Representation）模式；
- 程序语义正确，但生成代码不够高效；
- 修复这些遗漏优化往往需要经验丰富的编译器开发者手工完成。

近年来，LLM Agent 已经被用于自动修复软件 Bug，但作者指出：

> “遗漏优化修复”与传统 Bug 修复有本质不同。

传统 APR（Automated Program Repair）通常只需要：
- 测试通过即可；
- patch 满足已有 test suite。

但遗漏优化修复还需要：
- 从一个具体测试案例中“抽象”出更一般化的优化规律；
- patch 不仅修复当前例子，还要覆盖开发者真正期望的优化范围。

论文将这个问题定义为：

> “generalization-sensitive patching”
（对泛化能力敏感的补丁生成问题）

核心挑战在于：
- patch 太窄 → 只能优化单个 case；
- patch 太宽 → 可能引入错误或偏离开发者意图；
- patch 与开发者 intended scope 不一致。

因此论文关注的不是：
- “Agent 能否修复测试样例”
而是：
- “Agent 能否推断开发者真正想实现的优化泛化范围”。

# 2.1 Generalization 与 Optimization Scope

论文将一个 patch 看作一个 IR transformation：

定义：
- T(p)：patch 对程序 p 的变换；
- S(T)：该 patch 能正确优化的程序集合。

形式化定义：

S(T) = { p | T(p) defined 且 T(p) ≡ p }

其中：
- TG：开发者 golden patch；
- TA：Agent patch。

比较：
- G = S(TG)
- A = S(TA)

然后定义四种 scope 关系：

| 关系 | 含义 |
|---|---|
| A ⊂ G | Agent 泛化不足 |
| A ▷◁ G | 部分重叠 |
| G ⊂ A | Agent 泛化超过开发者 |
| A ∼ G | 范围一致 |

这是全文最核心的评价思想。
