## 摘要
大型语言模型（LLM）通常通过二元功能正确性来评估代码生成与程序修复能力：生成的程序或补丁要么通过测试套件，要么失败。该评估协议虽然简单，但较为粗糙，因为它忽略了部分进展、反馈利用、回归问题，以及模型通常借助这些过程逐步改进代码的精炼轨迹。我们提出了 PAIR-Bench，一种渐进式、自适应的代码改进评测基准，用于评估在反馈引导下将错误或不完整程序逐步改进为更正确程序的能力。PAIR-Bench 采用渐进式提示（progressive hinting），这是一种具有两个控制维度的结构化反馈协议。失败区域控制（failure-region control）通过将隐藏的失败测试分组为失败场景来决定反馈所针对的内容；提示深度控制（hint-depth control）则决定揭示多少与修复相关的信息，其范围从粗粒度症状到实现级指导。该设计使 PAIR-Bench 能够衡量模型是否修复了目标失败、是否能够超越提示进行泛化、是否保留了原本正确的行为，以及其需要多少辅助信息。通过使用渐进式指标评估修复轨迹，而不仅仅关注最终的通过/失败结果，PAIR-Bench 为评估大型语言模型的代码改进能力提供了更细粒度的方法。

## Abstract
Large language models (LLMs) are typically evaluated on code generation and program repair using binary functional correctness: a generated program or patch either passes or fails a test suite. This protocol is simple but coarse, as it ignores partial progress, feedback use, regressions, and the refinement trajectory through which models often improve code. We introduce PAIR-Bench, a progressive and adaptive benchmark for evaluating code improvement: transforming an incorrect or incomplete program into a more correct one through feedback-guided refinement. PAIR-Bench uses progressive hinting, a structured feedback protocol with two controls. Failure-region control determines what the feedback targets by grouping hidden failing tests into failure scenarios, while hint-depth control determines how much repair-relevant information is revealed, from coarse symptoms to implementation-level guidance. This design enables PAIR-Bench to measure whether a model repairs targeted failures, generalizes beyond the hint, preserves already-correct behavior, and how much assistance it requires. By evaluating repair trajectories progressive metrics rather than only final pass/fail outcomes, PAIR-Bench provides a finer-grained assessment of LLM code-improvement capability.

例如：

- 一个程序只错一个边界条件；
- 另一个程序所有测试都失败；

---

### （2）忽略“反馈利用能力”

现实中的 LLM 修复通常是：

- 先生成程序；
- 接收编译器/测试/自然语言反馈；
- 再逐步修改。

也就是说：

代码改进（Code Improvement）本质上是“交互式迭代优化过程”。

但现有 benchmark 只看最终结果，不看：

- 中间是否持续进步；
- 是否修复特定错误；
- 是否引入回归；
- 是否能够利用提示。

---

已有交互式 benchmark 的反馈往往：

- 某次可能收到“关键错误定位”；
- 另一次可能收到模糊描述；

导致结果高度波动。

因此：

现有 benchmark 实际测到的不只是模型能力，
还混入了“反馈质量随机性”。

# 2. 方法论：PAIR-Bench

## 整体思想

PAIR-Bench 的核心是：

“渐进式提示（Progressive Hinting）”

它把反馈控制拆成两个维度：

| 维度 | 含义 |
|---|---|
| Failure-region control | 提示针对哪个错误区域 |
| Hint-depth control | 提示暴露多少修复信息 |

然后：

- 逐轮修复；
- 逐轮评估；
- 记录完整修复轨迹。

---

# 2.1 Failure-region Control（失败区域控制）

## 核心思想

不是随机选择失败测试。

而是：

将隐藏失败测试划分成“失败场景（failure scenarios）”。

例如：

- 某类边界输入；
- 某条执行路径；
- 某种输出结构；
- 某类 runtime error。

---

## Failure Signature（失败签名）

每个失败测试由三部分组成：

### （1）Reference Execution Trace

正确程序执行过哪些代码行。

用于近似：

“行为路径”。

---

### （2）Expected Output Shape

输出结构：

- 单 token
- grid
- 多行
- binary line

等。

---

### （3）Candidate Failure Type

错误类型：

- timeout
- runtime error
- wrong token count
- wrong values

等。

---

## Scenario Grouping

具有相同 signature 的失败测试：

被聚合成同一个 scenario。

即：

G(k) = { j ∈ Fi,t : σ(j)=k }

作者强调：

这不是精确 bug root cause 推断，
而是：

“可复现的错误行为区域近似”。

---

# 2.2 Hint-depth Control（提示深度控制）

## 六级提示体系

PAIR-Bench 设计了六层 scaffolded hints：

| Level | 含义 |
|---|---|
| L1 | 仅症状 |
| L2 | 输入模式 |
| L3 | 状态跟踪问题 |
| L4 | 可疑代码位置 |
| L5 | 概念性修正 |
| L6 | 具体修复方向 |

---

## 示例

### L1

“输出比预期更大。”

仅描述现象。

---

### L3

“程序未正确维护重复值信息。”

开始涉及内部状态。

---

### L6

“修改 update logic，使重复值累积而非覆盖。”

已经接近修复方案。

---

## 设计目的

衡量：

模型需要多少帮助才能修复。

即：

- 强模型：
  - 用浅提示即可修复；
- 弱模型：
  - 必须给出深提示。

---

# 2.3 Progressive + Adaptive Policy

## Progressive（渐进式）

每轮：

1. 选择最大失败区域；
2. 生成对应 hint；
3. 模型修复；
4. 重新评估；
5. 转向其他 failure region。

目的：

让 benchmark 真正覆盖“错误空间”。

---

## Adaptive（自适应）

提示深度动态调整：

### 修复成功：

降低提示等级：

ℓ(t+1)=max(1,ℓt−1)

---

### 修复失败：

提高提示等级：

ℓ(t+1)=min(6,ℓt+1)

即：

- 成功 → 减少帮助；
- 失败 → 增加帮助。

类似：

IRT（Item Response Theory）
与教育学中的 scaffold learning。

---

# 2.4 轨迹级评测指标（核心贡献）

传统 benchmark 只有：

- pass rate

PAIR-Bench 引入大量 trajectory metrics。

---

## （1）TRS：Targeted Repair Success

衡量：

是否修复当前提示针对的 failure scenario。

---

## （2）BRG：Broader Repair Gain

衡量：

是否顺带修复了其他未提示错误。

即：

泛化能力。

---

## （3）BP：Behavior Preservation

衡量：

是否引入 regression。

---

## （4）PMR：Progress Monotonicity Rate

衡量：

修复轨迹是否单调提升。

---

## （5）HE：Hint Efficiency

衡量：

用了多浅的提示就完成修复。

越高表示：

越少依赖帮助。

---

## （6）Gap Closure

衡量：

修复了多少剩余错误空间。

---

## （7）Turns-to-Fix

衡量：

需要多少轮才能修复。
