## Abstract 

Capabilities of frontier models are often assessed using agentic benchmarks. To trust these results, benchmarks must accurately measure what they claim to and be free from inval-idating flaws. Previous manual audits of benchmarks such as SWE-Bench-Verified have uncovered several validity issues in transcripts. However, manual review is difficult to scale, and it is unclear whether automated methods can reliably surface flaws that compromise benchmark validity. In this paper, we developed AI scanners to detect four types of va-lidity issues: ground truth access, tool failure, guessing vulnerability, and answer format ambiguity. We produced grading rubrics for each to instruct human labeling, and evaluated the scanners against human labels on a held-out test set of Inspect Evals benchmarks. Our scanners identified several verified quality issues in five widely used benchmarks, including cases unlikely to be caught by random manual inspection. Not all cases were identified, and scanner performance varied substantially across benchmarks, criteria and models. We highlight several open challenges to be addressed to improve scanners for stronger quality-assurance claims, including broader standardization gaps in the evaluation field that degrade scanner performance. Together, these results serve as a proof of concept for using automated transcript analysis to audit benchmark quality more broadly. 

## 1 Introduction 

As models have grown more capable, evaluating them has required increasingly complex benchmarks. This complexity introduces new failure modes while making them harder to detect, bringing benchmark validity under greater scrutiny. The evaluations community has uncovered many flaws in widely used benchmarks— such as CORE-Bench (Kapoor, 2025a), SWE-Bench-Verified (Yu et al., 2025), and SWE-Bench Pro (Gabor, 1arXiv:2607.27518v1 [cs.AI] 29 Jul 2026 2026). To systematize these flaws, Zhu et al. (2025a) introduce the Agentic Benchmark Checklist (ABC) and use it to surface validity issues across a further ten evaluations. In SWE-Lancer, for example, they identify file system issues that could let agents access ground truth information, while in OSWorld several task samples contain broken links for websites. These flaws undermine the utility and interpretability of benchmark outcomes, making it challenging to accurately assess model performance. Benchmark utility depends on confidence in their validity. While reviewing code and datasets captures some invalidating flaws, many others are not obvious without a thorough review of the benchmark transcripts. Manual auditing of benchmarks is one way to increase confidence, but these audits can be time consuming or challenging for unassisted human researchers. Evaluation runs can require 100 million to 1 billion tokens per task (Folkerts et al., 2026; Adamczewski et al., 2026), making it infeasible to rely on manual review. Automated transcript analysis offers a potential path to scalable quality assurance. The open-source library Inspect Scout (Inspect Scout, 2026) can be used to build and run AI scanners, which are automated methods for detecting patterns in transcripts (Dubois et al., 2026). Using transcript analysis for identifying invalidat-ing flaws in benchmarks has only been minimally explored (Tu et al., 2026; Wang et al., 2026). For auditing to be systematic, we not only need a comprehensive set of validity criteria to measure, we also need reliable automated methods that can be standardized. This paper aims to bring this goal closer to feasibility by investigating the following questions: 1. Which evaluation quality criteria can and should be assessed using automated transcript analysis given current capabilities? 2. Given an existing issue or theoretical flaw in a benchmark, how many transcripts must be evaluated to determine whether a benchmark has at least one violation demonstrated? 3. What percentage of transcripts demonstrate these criteria violations in a set of existing benchmarks? 4. For transcripts which demonstrate violations (as determined by human graders), what is the perfor-mance of automated transcript analysis via scanners? From our investigations, we make the following contributions: 

• We identify a set of scanner-viable criteria for benchmark validity. 

• We develop scanners for a subset of four criteria (tool failure, guessing vulnerability, ground truth access, and answer format ambiguity) and validate their performance against human reviewers. 

• We outline a sampling methodology for how many transcripts must be evaluated, and implement a proof-of-concept that assesses the lower bound of confidence in a benchmark. 

• We open source our scanners and a dataset of transcripts across 11 agentic evaluations 

• We report verified issues our scanners identified in existing evaluations, some of which were difficult or impossible for our human reviewers to identify without assistance. 

• We identify several challenges with human auditing reliability, scanner elicitation requirements, and generalization across evaluations that could be resolved to improve scanner capabilities for quality assurance. Code: https://github.com/Generality-Labs/scanner_evaluation

22 Related Work 

2.1 Automated auditing within evaluations 

Existing auditing approaches within evaluations often focus on identifying specific types of violations and disqualifying them to prevent incorrect score inflation. For example, Rank et al. (2026) developed PostTrain-Bench which used an LLM-as-a-Judge to detect reward hacking. Their judge identified 23 contamination flags involving test data misuse across five agents when reviewing code, script outputs and data pipelines. PaperBench similarly relies on a judge, which checks for blacklisted URLs in agent logs and marks the flagged samples for review and disqualification (Starace et al., 2025). 

2.2 Transcript analysis tools and techniques 

Meng et al. (2025) introduced Docent, a transcript analysis tool, which they used to identify behavioral and scaffold issues in evaluations, such as benchmarks containing several unsolvable problems and models ignoring instructions. Meridian Labs (in collaboration with UK AISI) developed Inspect Scout (Inspect Scout, 2026), and Dubois et al. (2026) outlines a framework for log analysis using Inspect Scout scanners. Providing a refusal scanner case study, they highlight seven steps with accompanying rubrics to guide development of a scanner for more rigorous log analysis. 

2.3 Evaluation auditing work using transcript analysis 

Kapoor et al. (2025b) introduced the Holistic Agent Leaderboard (HAL) which compiled 21,730 agent rollouts across nine models and nine benchmarks. Using Docent, they detected a data leakage bug in a τ -bench few-shot agent, and design flaws in AssistantBench prompting. They analyzed benchmark transcripts across six categories (e.g. tool-use failures, instruction following, environmental barriers) using a binary yes/no flag rubric, finding that many task failures involved an instruction following violation. Wynne & Ududec (2025), from the UK AISI, use automated transcript analysis to audit pass-rate validity across 6,390 transcripts, finding quality issues that compromise capability claims, such as a model that refused roughly 30% of tasks through the submission tool rather than attempting them. Beyond targeted analyses, several efforts seek to automate benchmark auditing across large benchmark suites. Wang et al. (2026) introduced Auto Benchmark Audit (ABA), in which they used an agentic auditor to assess evaluation and agent quality across 168 benchmarks. They included transcript analysis on a subset of evaluation audits, finding that adding transcripts identified more major issues than the static assessments without them. Tu et al. (2026) developed BenchGuard, an automated benchmark auditing framework that they apply to two scientific benchmarks, ScienceAgentBench and BIXBench. On ScienceAgentBench, appending full agent transcripts improved recall from 83.3% to 91.7% for a single model, but this was inconsistent on BIXBench where only summaries of transcripts were available, indicating the importance of detailed agent transcript context when auditing benchmarks for flaws.

3.2 Identification of relevant criteria 

Not all of the criteria outlined in the Agentic Benchmark Checklist rubrics are best explored through tran-script analysis. For a criterion to be suitable, it must satisfy the following requirements: 1. Presence: Is the expression of a particular criterion theoretically possible in a transcript? 2. Verifiability: Can a criterion be confirmed to have been met or violated using a scanner or human? Other important considerations included whether the use of a scanner was sufficient for meeting the basic coverage requirement for the criterion. For example, state change comparison often requires comparing an external resource state which is a poor fit for scanners, or cases like T1 (Versions of all tools e.g., Python are clearly specified), where addressing the criterion can be achieved without transcript analysis. This excluded eight criteria. We identified eleven of the remaining criteria as particularly suitable for transcript analysis, 4and then selected a subset to develop into scanners. Full details of the exclusion/inclusion reasoning, and categorization of the criteria can be found in Appendix D.1. Mapping from criterion to scanners was not always exact. For example, multiple guessing criteria are proposed which become redundant when reviewed in the context of a transcript. We modified and expanded the chosen violation criteria in the ABC framework to better conform to transcript analysis, resulting in four scanner types covering various potential benchmark flaws (Table 1). 3.4 Evaluation selection 

After criteria selection, we used the following inclusion requirements to select the evaluations outlined in Table 3 for our development and test splits. 

Agentic Evaluations: We focused on agentic evaluations. Agentic describes an AI system that acts autonomously, using tools and taking multiple sequential actions, rather than producing a single response to a prompt. Our evaluation quality framework implicitly requires agentic evaluations, and transcript analysis is most useful for analysis of agent transcripts rather than non-agentic evaluations. Non-agentic evaluations were used for development set iteration on some criteria. See Appendix A.4 for non-agentic evaluation supplementary investigations. 

Common generation framework: We chose to review only benchmarks with an existing Inspect frame-work implementation. Using the same underlying framework allowed us to implicitly control for many potential variations in the data generation process, such as variable scaffolding and environmental setups. Using Inspect also made every evaluation we used compatible with Inspect Scout, our scanner framework, by default. 

Hardware and software requirements: Many of the evaluations we chose involved intensive research and development tasks as they primarily focused on the AI Research and Development subdomain. We used a combination of local and remote machine resources to meet hardware and software requirements, which are further detailed in the code repository. 3.5 Model selection 

Transcript Generation: We used GPT-5.4, Claude Sonnet 4.6, and GPT-5-mini to generate transcripts for review, with the default Inspect Evals configuration and scaffold. CVE-Bench (Zhu et al., 2025b) transcripts were available from a pre-existing dataset using Claude Opus 4.6. We primarily focused on GPT-5.4 and Claude Sonnet 4.6: both were the most recent mid-tier models from each model provider, which provided strong capability without the cost of running the flagship models to produce a large transcript set. Inclusion of GPT-5-mini allowed lower costs in our development set data, and also offered a point of comparison in transcript outputs to the other models. 

Scanner models: Both GPT-5.4 and Claude Sonnet 4.6 were chosen as our scanner models, which allowed us to compare performance between models and explore the generalizability of our scanner approach. 63.6 Data generation 

We divided transcripts into a development subset, used to iteratively develop the scanners, and a held-out test subset, used at the end of scanner development for the final frozen scanner. To produce the datasets, we collected transcript outputs from evaluations run with default configurations in Inspect Evals. CORE-Bench and SWE-Bench-Verified transcripts were used for both development and test sets, using mutually exclusive tasks for each. 

3.6.1 Synthetic data generation 

Naturally generated transcripts produced for the development set contained few clear violations, making it difficult to develop scanners using this data alone. To address low violation rates, we supplemented the development set with synthetic violations. We systematically modified task environments and prompts to produce failure modes while preserving the surrounding benchmark context. For each synthetic dataset, we implemented one or more variants corresponding to the predefined validity criteria. Where possible, the same violation pattern was instantiated across multiple benchmarks to support comparability. Importantly, this synthetic data was used to help inform development, but was not used in the final evaluation of the scanners. Synthetic manipulations were not applied to test set benchmarks, and synthetic data were not included in any of the subsequently reported performance metrics. A complete description of synthetic approaches is provided in Appendix E. 

3.7 Scanner development 

For the development of our Inspect Scout scanners, we broadly followed guidelines from Dubois et al. (2026). Each scanner prompt was developed iteratively on the human pre-labeled development dataset and the syn-thetic violation data. However we did not attempt to elicit upper bounded performance from our scanners in this effort. We identified several challenges with achieving a robust ground truth reference for sparse vio-lations, even with synthetic data usage, that must be addressed in future work for elicitation of a generalized scanner. See Appendix B for a case study on the ground truth scanner development, and results from the development set. 

3.8 Sampling size requirements 

We performed sample size calculations to identify grading requirements for validating our chosen criteria. We focused on three questions: 1) How many transcripts must be evaluated to determine whether a benchmark has an acceptably low violation rate? 2) How accurately can we specify the violation rate within a sample? and 3) How reliably do our scanners detect these violations relative to human graders? In our calculations samples (transcripts) are assumed to be I.I.D. and the confidence intervals are based on a normal approximation. Full details of the sample size calculations can be found in Appendix C. For 1), we set the acceptable error rate at <5%, which requires a minimum of ∼75 human graded and 

∼120 scanner graded transcripts under conservative assumptions of 80% human and 50% scanner sensitivity. These represent cases where, assuming zero violations are found in the transcripts, we can confidently rule out high violation rates in that benchmark/model combination. For 2), a sample size of ∼200 gives reasonable precision on violation rate estimates across a range of potential values for prevalence. This would provide halfwidths < ±5% if the true violation rate was less than 10%, and range up to around ±8% at true violation rates of up to 40% for human graders or strong scanners. For 3), estimating scanner sensitivity was the most demanding task, as it depends on the number of confirmed true positives rather than the total sample size. A dataset containing approximately 100 verified positives yields a usable estimate of sensitivity (e.g., ±8.5% for a true sensitivity of 0.85, or a lower bound near 0.78), but assembling this many positives was difficult when violations were rare, as a 10% prevalence would require manually screening on the order of 1,000 transcripts. 73.9 Post-validation sampling 

To maximize the efficiency of human grading for estimating scanner sensitivity on our test set data, we used a stratified post-validation design rather than a simple random sample to select transcripts for human review. Because true violations were expected to be rare, random sampling would result in few true positive examples providing limited information about scanner sensitivity. We therefore stratified transcripts by benchmark and scanner flag status, sampling both scanner-positive and scanner-negative cases within each benchmark to the extent available. A target of 25 scanner-positive and 25 scanner-negative samples per benchmark was used, using a threshold of ≥2 to differentiate positive and negative transcript-level flags. This produced an enriched dataset that was expected to contain a higher proportion of positive samples, allowing us to utilize human grading time more efficiently. However, even when using this approach we found it difficult to attain our sample size target of 100 verified positives, and the estimates of scanner sensitivity had wide confidence intervals as a result. 

3.10 Scanner performance metrics 

Scanner performance was quantified using human labels as the referent. Agreement on the ordinal 0–3 rubric was quantified using quadratic-weighted Cohen’s kappa (QWK), which accounts for the ordered nature of the labels and penalizes larger disagreements more heavily than adjacent-category disagreements. We also report binary classification metrics between scanner and human labels, using a threshold of ≥2 to differentiate positive and negative transcript-level flags. Because the post-validation design intentionally over-sampled scanner-flagged transcripts relative to their prevalence in the full test set, performance metrics on the test set were corrected using inverse-probability weighting (Horvitz & Thompson, 1952). Within each sampling stratum, each validated transcript was weighted by the inverse of its probability of selection, equivalent to the number of transcripts in the full stratum divided by the number validated from that stratum. Weighted counts of true positives, false pos-itives, true negatives, and false negatives were then used to estimate the reported population-level scanner performance metrics. This correction was unnecessary for the development set, as it consisted of a random sample and was fully labeled. Performance was quantified only using human labeled data, and synthetic data was not included. 

## 4 Results 

4.1 Test set post-validation 

We evaluated the performance of scanners in comparison to human grades on a stratified random sample of the test set transcripts. Scanners generally tracked human post-validation judgments, with a higher propor-tion of scanner flagged transcripts (i.e., labeled a 2 or higher) among those labeled as a 2 (clear violation) or 3 (impactful violation) by human graders (Figure 2). Full confusion matrices for each scanner are included in Appendix A.2 (Figure 7). In almost all cases, transcripts which demonstrated more severe violations, according to human graders, were also more likely to be flagged by scanners on average. The primary ex-ception was the tool failure scanner when using Claude Sonnet 4.6, which demonstrated approximately no discrimination ability based on human labels. Performance metrics, assuming human labels as correct, were calculated after reweighting to account for the sampling approach, and agreement with human grades was quantified by QWK (Table 4, Table 5). We also report two options for combining multiple scanner runs to maximize sensitivity (max, where a flag by either scanner is considered a violation) or reduce false positives (floor mean, emphasizing scanner agreement for violations). Performance was highly variable both across scanner models and across scanners. The F1 score, which is more useful than raw accuracy given the unbalanced nature of this dataset, ranged from 0.74 (0.59–0.86) for the GPT-5.4 guessing scanner to 0.14 (0.00–0.33) for the Sonnet 4.6 tool failure scanner. Answer Format Ambiguity: Exact matching to target values or text strings is used, but insufficient detail is provided on the required format for many tasks. For example, the number of significant digits required for floating point reports is not specified, which leads to spurious failures. In another example, the model is asked to report the color of a line (‘blue’) and functionally equivalent answers such as ‘light blue’ or hex codes for a matching color result in failure. 

Guessing: While correct answers require matching a specific target, the realistic answer space is often surprisingly small. In several examples, labels, axes, or colors are reported which come from a small and easily guessable set of options. In other cases, models successfully guess answers based on common characteristics of scientific papers (e.g., reporting a p-value as ‘ <0.05’) without actually completing a task. 

Tool Failure: Scanners frequently identified cases where models failed due to environment configuration issues. Environment configuration is an intended component of CORE-Bench, so this is not necessarily invalidating. However, these were by far the most common reasons for failure on the medium difficulty tasks, making it less useful for evaluating the primary aim of scientific paper reproduction. The frequent issues in this domain also obscured other configuration problems, such as command time-outs, external resource failures (e.g., vision model API calls), and other non-model technical issues which hamper model performance.

Answer Format Ambiguity: There was potential, persistent ambiguity around the specific output format requirements that occasionally led to model failures. ## 5 Discussion 

We found that Inspect Scout transcript scanners can be usefully implemented to help identify a range of benchmark weaknesses. Even with limited elicitation and no model fine tuning, our scanners identified several known issues in popular benchmarks, such as the contamination from ground truth data in SWE-Bench-Verified (Yu et al., 2025), as well as additional potential weaknesses, such as the vulnerability to guessing and ground truth access in CORE-Bench, which to our knowledge have not previously been reported. Scanner flag rates generally tracked human post-validation ratings of the same transcripts (Figure 2) and scanner judgments were broadly in agreement with human raters (Table 4). However, scanners in this work were not equivalent to human graders. Scanners often flagged transcripts that human graders later determined did not contain violations, suggesting that human verification of scanner flags is an important step when assessing benchmark quality. Conversely, a low rate of scanner-identified flags was consistent with a true lack of violations in that benchmark, as human graders only rarely identified violations in these benchmarks (Figure 3). We leveraged human transcript grading as the source of truth for evaluating scanner performance, but there are important caveats to this approach. Grading transcripts is challenging, particularly when they are long running or include difficult to read code execution and tool use. This may limit the grader’s ability to accurately identify violation examples, and it is possible that the human grades themselves contain undetected false negatives. In addition, the significance of a specific violation invariably relies on a subjective judgment that must take into account the overall context, the intent of the evaluation, and the practical considerations inherent to benchmark development. Human grades should therefore not be taken as a definitive judgement about the presence or absence of a violation, and interpretation of these results should be moderated as a consequence. The development of scanners involves numerous decision points, including the creation and refinement of prompts and rubrics, the inclusion of context outside the transcript, the selection of scanner models, and aggregation approaches to incorporate multiple scanners. This work focused primarily on breadth, exploring a range of vulnerabilities and benchmarks, rather than optimizing any specific configuration. It is therefore likely that a more focused approach targeted at a specific benchmark or violation type could identify addi-tional violations, or that scanners could be further optimized to generalize more broadly across a range of benchmarks. This work provides evidence that automated transcript analysis can rapidly flag suspicious transcripts, identify systematic failure modes, prioritize scarce human review, and support post-validation sampling strategies that yield more reliable estimates of benchmark-level quality. More generally, our findings point to a need for stronger benchmark documentation and validation standards as even this limited effort identified several potential issues in published benchmarks. The most promising near-term role for automated scanners 13 is their use in supplemental identification of potential issues, either during benchmark development or as a component of a broader verification audit. Automated scanners are unlikely to provide definitive proof that an evaluation is problem-free, but they can make benchmark auditing more systematic, scalable, and empirically grounded. 

5.1 Limitations and further work 

Our scanners were often effective at surfacing candidate violations, including issues that would have been difficult to detect through manual review alone. However, we encountered several limitations in our method-ology that should be considered when implementing this approach. 

• Transcript reliance and evaluation standardization: Scanners are unable to identify vulner-abilities that are not observable within the transcript itself. This makes them ill-suited for other potential benchmark vulnerabilities, such as issues with the scoring function or testing environment. In addition, not all evaluations provide the context useful for transcript analysis (e.g. ground truth answer is not always accessible to the scanner) which can lead to varying performance between evaluations. 

• Scanner optimization: In this effort we did not attempt any specific elicitation pipelines outside of manual prompt iteration, nor did we systematically vary other potential optimization targets like the inclusion of additional supporting context, token budget, or scanner model choice. A more dedicated effort targeting scanner optimization may produce more effective scanners, so our results should be treated as a reasonable lower-bound on scanner performance. 

• Dimension overlap for scanners: Some scanners were prompted to evaluate multiple dimensions simultaneously, which we observed led to some confusion in scanner model reasoning. For example, the guessing scanner assessed both the size of the answer space and whether the model in question explicitly attempted guessing. In general it may be preferable to develop more focused scanners for subsets of criteria. 

• Human grading challenges: Human graders in this work often had reasonable disagreements about whether specific examples qualified as violations, and this may undermine the utility of human grades as a desirable target for scanner performance. This may fluctuate widely depending on the criterion and whether the target is ambiguous or straightforward. It is possible that scanners, particularly when optimized to evaluate a specific benchmark, would outperform human graders in identifying potential benchmark vulnerabilities. 

• Generalization across evaluations: During testing on the held-out dataset, we encountered several instances of scanners failing to generalize to new contexts. For example, the development set did not include multi-turn messaging with a user, and we observed confusion on the multi-turn Tau2-bench for one of the scanner models. Providing robust tooling for evaluation standards over complex and diverse sets of inputs remains a challenge. 

• Red teaming agents: The behavior of the transcript generating model impacted the flag rate of the scanner, as cases where the model attempted to circumvent the benchmark (e.g., by guessing the answer) were more likely to be flagged than other cases where the model attempted the task in good faith. This suggests that scanners could be combined with intentionally designed red team agents that attempt this sort of reward-hacking, which may allow more efficient identification of any vulnerabilities in the benchmark. 

## 6 Conclusion 

This study demonstrates that automated transcript analysis can provide a scalable and practical layer of quality assurance for AI benchmark validation. Across four validity criteria, scanner-assisted review identified multiple verified issues in widely used benchmarks, including flaws that would be difficult to find through 14 random manual inspection alone. However, scanner performance varied by benchmark, validity criterion, and judge model, and many judgments required contextual understanding of the benchmark’s intended design. Further investigations into elicitation and improving generalization across benchmarks would be needed to support the use of scanners for assurance claims of benchmark quality. These findings support the use of scanners as a supplemental tool that can surface suspicious transcripts, guide targeted human review, and reveal systematic weaknesses in benchmark construction. As AI evaluations become more consequential and increasingly aggregated into broader claims about model capability, scalable validation workflows of this kind will be essential for improving benchmark reliability and interpretability.

A.4 Scanner results on non-agentic evaluations 

We also chose to run our scanners on two non-agentic evaluations (HLE (Phan et al., 2025) and GPQA (Rein et al., 2024)) for the answer format ambiguity and guessing scanners. 23 For GPQA, the guessing scanner flagged most samples as a 2 or higher, given that there were limited options for each multiple choice question to choose from, which made the tasks inherently guessable. The answer format ambiguity scanner did not flag violations for GPQA, as it was extremely clear in its requirements. For HLE, many samples were flagged for violations on the multiple choice questions. It was unclear whether the output should be multiple answers, response with the full letter and description, or just the letter. Comparatively to other non-agentic benchmark instructions like GPQA, answer format instructions were not clearly specified in many such cases. However HLE also highlighted some scanner cases where the scanner mistakenly identified the scanner prompt itself as part of the question prompt, due to a change in input formatting between non-agentic and agentic benchmarks. While easily fixed, it does highlight a challenge with automating audits across benchmarks where available information and structure to collect from can vary widely.

24 B Ground truth access development case study 

B.1 Development using human graded transcripts 

Initial development of the ground truth scanner involved producing transcripts from the development set evaluations chosen for the scanner and grading the transcripts to find naturally occurring violations in the evaluations. Violations were labeled on a scale from 0 (no violation) to 3 (clear and impactful violation leading to a pass). 

Figure 12: Human labeled ground truth access violations for benchmarks with standard settings (left) and confusion matrices between human graders and scanners (right). The CORE-Bench easy split were all graded as containing a potential violation, as each sample provides the model with access to all code, which the agent can (and does) use at times to circumvent the actual task (see Figure 4). In all other benchmarks for ground truth development, very few violations were identified. 

B.2 Development using synthetic violations 

To compensate for the low violation rate identified through human grading, we supplemented this dataset with several iterations of synthetic data generation. Full generation details are in Appendix E. While 100% of contamination samples provide the model with the gold solution, this is rarely demonstrated clearly in the transcript itself. Despite access to the gold solution, models often choose to perform the task in good faith even to the point of failing the task using an independently derived solution. Cases where the model was instructed to reveal this ground truth access (e.g., by announcing the fact or conducting a disallowed web search) were almost always flagged, but these cases are much less realistic. 

B.3 Ground truth scanner development set results 

For iteration of the scanners against the human labeled and synthetic datasets, scanner performance was quantified against the human labels. Disagreements between scanner and human grades were manually reviewed to identify potential failure modes and iteratively improve the scanners. Using quadratic-weighted Cohen’s kappa (QWK), the scanners had only modest agreement with the pre-collected human data (QWK = 0.418 for Sonnet 4.6, QWK = 0.500 for GPT-5.4), with the most frequent disagreements occurring between scores of 0 (no violation) and 1 (potential violation). The scanners were generally more sensitive to violations than human graders, particularly when flagging potential violations (label = 1). This is desirable, as potential violations can be subsequently reviewed for a final determination while a score of 0 may be more likely to pass unnoticed. 27 C Sample size calculations 

This appendix provides a worked example of the sample size calculations performed to set targets for human post-validation and scanner performance metrics. It is split into three separate plausible research questions, which require increasing investment in data collection to achieve robust results. These sample size calcula-tions are generally applicable, and can be used as guidance for any similar approach interested in addressing these questions around evaluation robustness. 

C.1 Research questions 

For the identified scanner objectives, there are three relevant research questions: 

• How many transcripts must be evaluated to determine whether a benchmark has at least one violation demonstrated? (C.2) 

• What percentage of transcripts demonstrate this violation for a given benchmark? (C.3) 

• For transcripts which demonstrate violations (as determined by gold standard human graders), how often is this violation detected by automated transcript analysis via scanners? (C.4) These sample calculations are approximations and involve various assumptions that are noted in each section. In all analyses, samples (transcripts) were assumed to be I.I.D. and the confidence intervals are based on a normal approximation. These assumptions may result in underestimated confidence intervals in practice, particularly in cases where the violation rates are extremely rare or scanners are extremely precise. However, the I.I.D assumption may result in overly conservative confidence intervals in cases where benchmarks are highly correlated, such as when they are generated formulaically. The impact of these assumptions is expected to be modest in most cases. 

C.2 Identifying at least one violation 

Summary: For sampling planning, we set the acceptable error rate at <5%. This requires a minimum of ∼75 human graded and ∼120 scanner graded transcripts under conservative assumptions (Se of 0.8 for humans, or 0.5 for scanners). These represent cases where, assuming 0 violations are found in the transcripts, we can confidently rule out high violation rates in that benchmark/model combination. The choice of this threshold is arbitrary, and the threshold could be tightened with a larger sample size. Even when violations have been identified as theoretically possible via code review/testing, these may not happen in practice in a way that is identifiable in transcripts. In some cases a benchmark may contain hundreds of questions generating lengthy transcripts, and manually reviewing every transcript may not be feasible. It is therefore helpful to know how many transcripts must be reviewed to bound the true error rate below some threshold (e.g., <5% violation rate with 95% confidence). This can be thought of as a test to determine whether a benchmark should be given a passing grade for a given criterion. This question is applicable to both human and scanner graders, as the calculations are identical but make different assumptions (i.e., scanners may have lower sensitivity than human graders). In this analysis, we assume that the grader has functionally 0 false positives (specificity = 1). This reflects a scenario where each putative positive is verified after initial labeling, which is accomplished by having multiple graders (with adjudication of disagreements) to validate positives. In most intended applications this assumption is valid, as a benchmark should not be considered flawed without verifying the existence of violations. If this assumption is not valid (e.g., fully automating the grading of benchmarks without a human in the loop), the sample size needed would be much larger and the minimum threshold would be bounded by the false positive rate. The number of samples needed to identify at least one true violation (positive) is a function of both the true prevalence ( p0), the sensitivity (Se) and specificity (Sp = 1) of the grader, and the desired confidence. Sample size requirements are shown for various assumptions of these parameters, with the desired confidence held steady at 95%. 28 Figure 15: Sample size needed to identify at least one violation. Sample size estimates assume 0 false positives (after adjudication of putative positives), and are calculated for various sample sizes and baseline prevalence rates. The most relevant term here is p0 which sets the desired error tolerance for marking a benchmark as passing. Based on this analysis, an acceptable violation rate of <5% would require >119 transcript reviews under the most conservative estimate (Se = 0.5, or 50% miss rate on positives), or >199 if the desired error rate is 

<2.5%. Human graders might be assumed to have Se ≈ 1, in which case only >59 and >99 samples would be required, respectively. The sample size is highly dependent on the desired error tolerance, which is important for both planning and reporting purposes. Without an extremely large sample size, it is functionally impossible to rule out very low error rates. However, extremely low error rates are likely acceptable from a benchmark evaluation perspective. 

C.3 Estimating violation rate (prevalence) 

Summary: For planning purposes, a sample size of ∼200 gives good precision across a range of potential values for prevalence. This provides halfwidths < ±5% if p ≤ 0.10 , and ranges up to around ±8% at p = 0 .4

for human graders or strong scanners. Weaker scanners would have somewhat less precision, but still enough to reasonably report results. Section C.2 deals with the case where no violations are found in the transcript, so the benchmark can be marked as passing for that criterion. In this section we deal with the case where violations are discovered in transcripts, and we would like to know how impactful those violations are (i.e., how important is the presence of these violations for interpreting benchmark results). The required sample size here is determined primarily by the desired precision on this estimate: how narrowly we want to bound the true error rate based on a sample. This can be approached in two complementary ways, either bounding the confidence in absolute terms (e.g., estimates within ±5%) or in relative terms (e.g., estimates within ±0.5 times estimate). The number of samples required is a function of the same factors as in section 1 ( P0, Se, Sp, and assumed 95% confidence interval), plus the desired confidence interval width. Sample size requirements are shown for 29 various assumptions of these parameters (Figure 16). These assume a validation approach as in section 1 (so there are no false positives), though this assumption is less critical in this case and a modestly sensitive grader (Se = 0.8). 

Figure 16: Sample size needed to bound estimate of prevalence. 

Here the colors indicate various ‘ground truth’ violation rates and the y axis indicates the desired precision (either relative or absolute). Choosing a sample size from these plots means balancing the desired precision across various potential scenarios that may be encountered. This can be done in either direction, either assuming a desired precision and finding the sample size or assuming a maximum sample size and determining the precision. As an example, we may want a confidence interval around ±5% as long as p < 0.10 , but if p > 0.10 we’d accept a wider interval (no more than 50% the value of p, so for p = 0 .20 the halfwidth is ±10%, and for 

p = 0 .40 the halfwidth is ±20%). We would use the sample size from the first plot for p < 0.1 and from the second plot for p ≥ 0.1 to find the maximum required sample size, which in this case is 177. This sample size does depend somewhat on the grader sensitivity (Figure 17). With a Se = 0.95 ( ∼human grader) the sample size is reduced to 147, while if the grader is much worse (Se = 0.50, conservative for scanner), the sample size is increased to 292. From a planning perspective, this means we should expect to require more samples from scanner grading to get a precise estimate of true prevalence than we require from human graders. 

C.4 Estimating scanner sensitivity 

Summary: A sample with 100 true positive labels gives relatively good power to estimate Se in real data (±8.5% CI if true Se is ∼0.85, or a lower bound of 0.778). However, if violation rates have low prevalence the primary issue may be sourcing a large number of positive samples. Unless scanners achieve near perfect performance, it is expected that any flagged potential violations are validated by a human user. In this scenario false positives are not particularly damaging (unless they are very common) because they can easily be dealt with by the user, so the metric of interest is sensitivity/recall (what fraction of true positives are identified by the scanner). Determining sensitivity requires identifying the number of true positives (TP) and false negatives (FN), so the only relevant factor is the number of labeled positives (though negatives are also useful for other diagnostics like F1 score). To determine study power, we calculate the half width on the Se estimate from a given sample size of positives. This will depend on the Se, but even for a relatively poorly performing scanner (Se = 0.5) the true Se is bounded within ±10% with 100 positive samples (Figure 18). It is also possible to ascertain the ‘lower bound’ on the sensitivity, given n positive samples, which might be more useful for planning as it can provide a minimum guarantee on scanner efficacy (Figure 19). 30 Figure 17: Relative precision for graders with different sensitivities. Sensitivity is compared for either optimistic (human grader or excellent scanner, left) or conservative (right) assumptions. Reduced sensitivity requires a much larger sample size to bound the true error rate with confidence. 

Figure 18: Estimates of CI halfwidth for various sample sizes. Required sample size depends on both the sensitivity of the scanner (Se) and the desired halfwidth. When violations are common this is relatively easy, as it is straightforward to build a labeled dataset with enough true positives by random sampling. However, we should expect in most cases that violations are relatively rare, as if they were common they would presumably have been identified during benchmark 31 Figure 19: Lower bound on estimate of Se given known true Se and sample size (of positives).

All synthetic generation followed a common ruleset designed to keep the manipulated transcripts as close to real scanner-input distribution as possible: 

• System messages were stripped from scanner-visible transcripts. When a system prompt was used to create synthetic data, the scanner did not have access to the injected system content. 

• Up to three variants per violation per benchmark. Where the behavior warranted it, we pro-duced multiple variants of a given violation (e.g. differing in how directly the agent was encouraged to use leaked information), targeting up to three variants per criterion per evaluation, and reusing variant designs across benchmarks where feasible. 

• Structural alterations to the task were minimized. We avoided user prompt or environ-mental setup changes that qualitatively changed the intended benchmark task. Where we removed supporting tools or supporting context, we left the underlying task objective largely unchanged.
