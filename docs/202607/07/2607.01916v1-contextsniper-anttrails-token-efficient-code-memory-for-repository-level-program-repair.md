## 摘要
大型语言模型智能体能够修复真实代码仓库中的问题，但它们往往会在整文件读取、广泛搜索以及冗长终端输出上消耗大量上下文预算，而其中有用证据常与无关代码和日志混杂。本文提出 ContextSniper，这是 AntTrail 面向仓库级程序修复的高 token 效率代码记忆层。作为 AntTrail 更广泛智能体记忆引擎中的代码专用模块，ContextSniper 实现了用于精确证据选择的 Sniper 功能：它检索候选代码与运行时证据，利用混合检索信号进行排序，通过具备意图感知能力的上下文门控过滤长输出，并在提示词之外保留可恢复的源代码上下文的同时，返回紧凑的证据包。我们在 SWE-bench Lite 上使用 OpenClaw 和 Claude Code 对 ContextSniper 进行了评估，在每种主机—智能体条件下运行 50 个任务。对于 OpenClaw，ContextSniper 将总 token 使用量降低了 51.5%，记录成本降低了 36.4%；对于 Claude Code，总 token 使用量降低了 38.9%，估算成本降低了 27.3%。已提交问题的解决率略有下降：OpenClaw 从 26.0% 降至 24.0%，Claude Code 从 32.0% 降至 30.0%。ContextSniper 的试点测试脚本已开源，地址为 https://github.com/Calluking/ContextSniper

## Abstract
Large language model agents can repair real repository issues, but they often spend large context budgets on whole-file reads, broad searches, and long terminal outputs where useful evidence is mixed with irrelevant code and logs. This paper presents ContextSniper, AntTrail's token-efficient code memory layer for repository-level program repair. As the coding specialization of AntTrail's broader agent memory engine, ContextSniper implements the Sniper feature for precision evidence selection: it retrieves candidate code and runtime evidence, ranks it with hybrid retrieval signals, filters long outputs through an intention-aware context gate, and returns compact evidence packets while preserving recoverable source context outside the prompt. We evaluate ContextSniper on SWE-bench Lite with OpenClaw and Claude Code, using 50 task runs per host-agent condition. ContextSniper reduces total token use by 51.5% and logged cost by 36.4% for OpenClaw, and reduces total token use by 38.9% and estimated cost by 27.3% for Claude Code. Submitted-resolution rates decrease slightly, from 26.0% to 24.0% for OpenClaw and from 32.0% to 30.0% for Claude Code. ContextSniper's pilot testing scripts are open-sourced at https://github.com/Calluking/ContextSniper

### 研究背景

随着 SWE-bench、SWE-agent、Claude Code 等仓库级（repository-level）软件工程代理的发展，大语言模型（LLM）已经不再只处理单函数代码生成，而是需要：

这类任务的核心难点不再只是“生成代码”，而是：

> 如何在海量仓库上下文中找到真正有价值的修复证据（repair evidence）。

---

### 当前系统的问题

现有代码代理通常采用“原始仓库访问（raw repository access）”方式：

- 大范围 grep；
- 整文件读取；
- 长 terminal 输出；
- 重复测试日志；
- 多轮失败后重复读取。

导致：

#### 1）Token 开销巨大

随着交互轮数增加：

- prompt context 持续膨胀；
- 后续每轮推理都需携带历史噪声；
- inference cost 与 latency 急剧增加。

---

#### 2）上下文污染（Context Flooding）

真正关键的信息可能只有：

- 一条 assertion；
- 一个 import；
- 某个 symbol；
- 某个 stack trace。

但它们被淹没在：

- helper code；
- build log；
- 重复 traceback；
- 无关函数；
- 早期失败尝试中。

论文认为：

> “上下文长度增加 ≠ 有效证据增加”。

---

### 论文核心目标

论文提出：

> ContextSniper：一个位于“代码代理”和“仓库”之间的 Token-Efficient Code Memory Layer。

其目标不是替换 agent，而是：

- 将 noisy repository context 转换为 compact evidence packet；
- 保持 source-grounded 可恢复性；
- 降低 token 与推理成本。
