## 摘要
基于大语言模型（LLM）的软件工程智能体正越来越多地被开发用于根据问题报告和代码仓库生成补丁，以解决软件问题。错误复现测试（Bug Reproduction Tests，BRTs）是此类智能体的重要组成部分，并已被证明对补丁验证具有实用价值。然而，BRT 是否也能帮助更核心的补丁生成阶段仍不明确。我们首先开展了一项初步研究，发现直接使用先进的 BRT 生成器来引导补丁生成并无益处：fail-to-fail 类型的 BRT 可能误导智能体，而即使是 fail-to-pass 类型的 BRT，其收益也有限甚至为负。我们的分析揭示了两个原因：其一，fail-to-pass BRT 可能仅覆盖所报告问题的一种表现形式，从而导致生成不完整的补丁；其二，fail-to-fail BRT 作为直接的补丁生成目标并不可靠。受这些发现启发，我们提出了 SWE-Doctor，一种利用来自多面向 BRT 执行的运行时诊断信息来引导补丁生成的软件问题解决智能体。SWE-Doctor 首先针对问题中陈述的不同行为需求生成多面向 BRT，然后执行并调试这些 BRT，以构建基于运行时信息的诊断记录，最后结合在 BRT 生成过程中推断出的定位信息，利用这些诊断结果引导补丁生成并减少不完整补丁。我们在广泛采用的 SWE-bench Verified 和 SWE-bench Pro 上，针对 Python 缺陷修复问题并结合五种 LLM 后端对 SWE-Doctor 进行了评估。SWE-Doctor 在全部 10 种 LLM-基准组合中均持续优于现有智能体，在 SWE-bench Verified 上的平均问题解决率达到 75.7%，在 SWE-bench Pro 上达到 59.4%。特别是在更具挑战性的 SWE-bench Pro 上，SWE-Doctor 相比基线智能体将平均问题解决率提高了 8.0 至 8.9 个百分点。

## Abstract
Large language model (LLM)-based software engineering agents are increasingly developed to resolve software issues by generating patches from issue reports and code repositories. Bug reproduction tests (BRTs) are an important building block for such agents and have been shown useful for patch validation. However, it remains unclear whether BRTs can also help the more central stage of patch generation. We first conduct a preliminary study and find that directly using advanced BRT generators to guide patch generation is not beneficial: fail-to-fail BRTs can mislead agents, while even fail-to-pass BRTs bring limited or negative gains. Our analysis reveals two reasons: fail-to-pass BRTs may cover only one manifestation of the reported issue, leading to partial patches, whereas fail-to-fail BRTs are unreliable as direct patch-generation targets. Motivated by these insights, we propose SWE-Doctor, a software issue resolution agent that guides patch generation with runtime diagnoses derived from multi-faceted BRT executions. SWE-Doctor first generates multi-faceted BRTs for different behavioral requirements stated in the issue, then executes and debugs these BRTs to construct runtime-grounded diagnosis records, and finally uses the diagnoses together with localization information inferred during BRT generation to guide patch generation and reduce partial patches. We evaluate SWE-Doctor on Python bug-fixing issues from the widely adopted SWE-bench Verified and SWE-bench Pro across five LLM backends. SWE-Doctor consistently outperforms existing agents across all 10 LLM-benchmark combinations, achieving average resolution rates of 75.7% on SWE-bench Verified and 59.4% on SWE-bench Pro. In particular, on the more challenging SWE-bench Pro, SWE-Doctor improves the average resolution rate by 8.0-8.9 percentage points over the baseline agents.

### 研究背景

近年来，基于大语言模型（LLM）的软件工程智能体（Software Engineering Agents）快速发展，典型任务包括：

- 根据 issue report 自动定位缺陷
- 浏览代码仓库
- 修改源代码
- 运行测试并生成补丁

其中，Bug Reproduction Test（BRT，缺陷复现测试）已经被广泛用于：

- 验证补丁是否修复问题（patch validation）
- 将自然语言 issue 转化为可执行反馈

但已有工作主要将 BRT 用于“补丁生成之后”的验证阶段，而不是“补丁生成过程中”的指导。

---

### 论文要解决的核心问题

作者研究的问题是：

> “BRT 能否直接帮助补丁生成，而不仅仅是补丁验证？”

作者首先发现：

- 直接让 agent “把 BRT 修到通过”并不可靠
- 甚至先进 BRT 生成器也无法提升整体修复率

进一步分析发现两类问题：

#### （1）Fail-to-Pass BRT 的问题

即：

- 测试在 buggy repo 上失败
- 在 ground-truth patched repo 上通过

看似合理，但：

- 往往只覆盖 issue 的一个行为侧面
- 导致 agent 生成 partial patch（局部修复）

例如：

- issue 实际需要修改两个代码路径
- BRT 只覆盖其中一个路径
- agent 修复后测试通过，但 issue 实际未完全解决

---

#### （2）Fail-to-Fail BRT 的问题

即：

- 测试在修复前后都失败

此类测试：

- 无法作为可靠 patch target
- 会误导 agent 朝错误方向修改代码

---

### 论文整体意义

论文提出一个重要观点：

> “BRT 的真正价值不在于 pass/fail 本身，而在于执行过程中的运行时诊断信息（runtime diagnosis）。”

因此：

- 不应把 BRT 当成简单 oracle
- 而应把它当成“调试探针（debugging probe）”

这是本文最核心的思想转变。

# Stage 1：多面向 BRT 生成（Multi-Faceted BRT Generation）

## 核心思想

不是只生成一个 reproduction test。

而是：

> 从 issue 中抽取多个行为需求（behavioral requirements），为每个需求生成对应 BRT。

---

## 关键步骤

### （1）需求分解（Requirement Extraction）

LLM 从 issue report 中提取：

- 输出行为
- 异常条件
- 兼容性要求
- 边界行为

每个 requirement 被视为：

- issue 的一个 facet（侧面）

作者强调：

- 不允许自由总结
- 必须严格基于 issue 文本

目的是降低 hallucination。

---

### （2）Requirement-Level Localization

针对每个 requirement：

- 先做代码定位
- 再生成 BRT

定位方式结合：

- identifier matching
- LLM localization

得到：

- 相关文件
- 相关函数

---

### （3）Generate–Execute–Refine Loop

BRT 不是一次生成。

而是：

```text
生成测试
   ↓
执行
   ↓
分析失败原因
   ↓
若失败原因不符合 requirement
   ↓
继续修正测试
```

停止条件：

- 测试确实因目标 requirement 而失败

---

### （4）Execution-Based Screening

过滤无效测试：

保留：

- assertion failure
- meaningful exception

过滤：

- 环境错误
- 缺依赖
- 未触达目标代码

因为这些无法提供 runtime diagnosis。
