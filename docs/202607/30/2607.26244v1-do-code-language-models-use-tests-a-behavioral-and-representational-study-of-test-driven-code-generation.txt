Abstract 

Public test cases are widely used to improve code generation with large language models, yet it remains unclear whether models genuinely use these tests as executable specifications or merely react to them as additional prompt context. We present a behavioral and representational study of test-driven code generation across HumanEval+, MBPP+, and recent LiveCodeBench problems. We compare natural-language-only prompting with prompts augmented by visible tests, shuffled tests, irrelevant tests, assertion-only tests, and syn-thetic tests generated by a stronger model. Beyond pass-rate evaluation under EvalPlus hidden tests and the official Live-CodeBench runner, we analyze per-task behavioral flips, lin-ear probing results, and layer-wise hidden-state shifts induced by different test contexts. Our primary Qwen2.5-Coder-7B re-sults show that visible tests substantially improve performance on MBPP+, but the effect is dataset-dependent and weak on HumanEval+ and recent LiveCodeBench tasks. A Qwen3.6-27B robustness study raises the LiveCodeBench NL-only pass rate from 13.1% to 39.4%, yet relevant original tests add only 2.9 points ( p = .458 ) and synthetic high5 tests add 1.7 points over their matched baseline ( p = .701 ). Increasing the number of tests produces larger internal representation shifts, while performance gains quickly saturate or disappear. Assertion-only and irrelevant-test prompts can strongly perturb hidden states without improving correctness, suggesting that repre-sentational change alone is not evidence of effective test uti-lization. After controlling for added prompt length, task-level shifts are associated with both beneficial and harmful behavior flips, but the association is substantially stronger for harms. Across both model scales, stronger and more numerous public tests do not reliably improve performance on difficult Live-CodeBench problems. These findings indicate that test cases influence code models through a mixture of semantic guidance and prompt-context perturbation, and provide practical diag-nostics for studying when test-driven prompting truly helps. 

## Introduction 

Large language models (LLMs) have become effective tools for code generation, with standard benchmarks such as Hu-manEval and MBPP measuring whether generated programs pass unit tests (Chen et al. 2021; Austin et al. 2021). Be-cause natural-language programming tasks are often under-specified, a natural extension is to include public tests in the prompt. This test-driven style of prompting is appealing: tests look like partial executable specifications, and recent work has reported that adding them can improve code gen-eration accuracy (Mathews and Nagappan 2024; Fakhoury et al. 2024). However, it is not obvious what a code model is doing when public tests help. One possibility is semantic test utilization: the model interprets the input-output behavior expressed by the tests and synthesizes a program that satisfies the intended specification. Another possibility is prompt-context pertur-bation: tests alter the local distribution, length, syntax, or examples in the prompt, nudging the model toward different completions without reliable semantic use of the test cases. These explanations have different implications. If models use tests as specifications, better tests should consistently help, irrelevant tests should hurt, and internal representations changed by tests should align with improved correctness. If tests mainly perturb the prompt, performance changes may be unstable, shuffled or irrelevant tests may have comparable effects, and large hidden-state shifts may not imply better programs. This paper asks: Do code language models actually use public tests in test-driven prompting? We study this question with both behavioral and representational diagnostics. Be-haviorally, we compare pass rates and per-task flips between prompt conditions. Representationally, we collect prompt-end hidden states, train simple probes, and measure layer-wise shifts relative to natural-language-only prompts. We evaluate Qwen2.5-Coder-7B-Instruct (Hui et al. 2024) on HumanEval+ and MBPP+ using EvalPlus hidden tests (Liu et al. 2023; EvalPlus Team 2023), and on the latest problems newly added in LiveCodeBench release v6 relative to release v5 (Jain et al. 2024; LiveCodeBench Contributors 2025). We then repeat the LiveCodeBench original- and synthetic-test experiments with Qwen3.6-27B (Qwen Team 2026) as a stronger-model robustness check. Our study makes three contributions. First, we show that public tests can help substantially on MBPP+ but not con-sistently across datasets. On MBPP+, adding public tests improves hidden-test pass rate from 63.8% to 71.2%. On HumanEval+, performance is already high and unchanged by public tests, while on recent LiveCodeBench tasks the gain is only 1.7 points and is matched or exceeded by irrel-evant tests. Second, we show that test-induced hidden-state changes are real but not sufficient for correctness. Test quan-tity increases hidden-state shift, and prompt condition is lin-arXiv:2607.26244v1 [cs.SE] 28 Jul 2026 early decodable from intermediate layers, yet assertion-only and irrelevant-test prompts often shift representations more than useful public tests while performing worse. Third, we generate synthetic public tests with a stronger model to sep-arate weak public tests from model limitations. On MBPP+, synthetic tests reproduce part of the public-test benefit. On recent LiveCodeBench tasks, stronger and more numerous synthetic tests increase representation shifts but do not im-prove pass@1 beyond original or irrelevant-test prompts. This conclusion persists with Qwen3.6-27B: the model is substantially more capable, but neither original nor synthetic tests produce a statistically reliable paired improvement. Fig-ure 1 summarizes the central empirical pattern: public tests are useful when they produce favorable behavior flips, but larger representational shifts alone do not guarantee better code. 

## Experimental Setup 

Datasets 

We evaluate on three families of code generation tasks. 

HumanEval+ and MBPP+ are EvalPlus versions of Hu-manEval and MBPP with expanded private tests for more rigorous functional correctness evaluation (Liu et al. 2023; EvalPlus Team 2023). We use three public tests per task as the default visible-test budget, following prior TDD-style code generation work (Mathews and Nagappan 2024). 

LiveCodeBench v6-new contains 175 problems that ap-pear in LiveCodeBench release v6 but not release v5 (Live-CodeBench Contributors 2025). These problems are more recent and more difficult: the subset contains 43 easy, 52 medium, and 80 hard problems from AtCoder and Leet-Code. We strip public examples from the problem statement and expose public tests only through controlled prompt con-ditions. 

Models and Evaluation 

Our primary generator is Qwen2.5-Coder-7B-Instruct, loaded locally with greedy decoding. For HumanEval+ and MBPP+, we evaluate generated code with EvalPlus hid-den tests. For LiveCodeBench, we use the official Live-CodeBench runner and report pass@1. All generation con-ditions are run with the same model, decoding settings, and maximum token budget within each dataset. For the stronger-model extension, we evaluate Qwen3.6-27B in BF16 with greedy decoding, thinking disabled, and at most 8192 new tokens. We use eight A800 GPUs, running one independent vLLM 0.25.1 replica per GPU. Generation and state collection are separated: vLLM performs batched autoregressive decoding, while Transformers 5.14.1 replays the exact prompt once to collect the prompt-end hidden state from all 64 transformer layers. We hash prompt token IDs and accept a state only when the vLLM and Transform-ers hashes agree; all 1,400 states across the original and synthetic-high5 runs pass this check. We disable thinking because an exploratory pilot exhausted the 8192-token bud-get on 568 of 700 generations, with 564 never closing the reasoning segment. The final non-thinking protocol avoids this output-length confound and better matches the Qwen2.5-Coder setup. Under this protocol, 29 of 700 original-test out-puts and 27 of 700 synthetic-high5 outputs reach the length cap; they remain in the official pass@1 evaluation as gener-ated. 

Prompt Conditions 

For each task, we construct several prompt conditions: 

• NL-only : the task prompt without visible tests. 

• NL+tests : the task prompt plus relevant public tests. 

• Shuffled tests : the same test inputs but with expected outputs shuffled across tests. 

• Irrelevant tests : visible tests borrowed from a different task. 

• Assertion-only : the function signature and visible tests, but without the natural-language problem description. 

• Test-names-only : a control that includes test labels or function names but removes input-output assertions. The contrast between relevant, shuffled, and irrelevant tests probes whether improvements depend on test semantics rather than merely adding test-like context. The assertion-only condition asks whether tests alone are enough to recover the intended program. 

Synthetic Public Tests 

To study test quantity and test quality, we generate additional public tests with a stronger API model. For HumanEval+ and MBPP+, generated assertions are filtered by syntax, duplicate removal, and execution against the reference solution. We then select high-scoring, low-scoring, random, or diverse tests according to a lightweight quality heuristic and evaluate prompts containing one to three tests. For LiveCodeBench, where no reference solution is available in the benchmark rows, we generate public input-output test cases in the official format, validate their format, remove duplicates, and keep the original private tests for evaluation. This design uses synthetic tests only as prompt context; official hidden/private evaluation remains unchanged. 

Behavioral and Representational Analyses 

We use three analysis tools. Behavior flips compare two conditions for the same task. A gain occurs when the base condition fails and the target condition passes; a loss occurs when the base passes and the target fails. The net gain is gains minus losses. We use a two-sided exact McNemar test, equivalently an exact binomial test over discordant pairs, to assess whether gains and losses differ. For direct com-parisons between relevant and control tests, we also report Newcombe score intervals for paired pass-rate differences and apply Holm correction across eight original-test con-trasts. Difficulty-stratified LiveCodeBench comparisons use the same paired analysis and are treated as exploratory.

## Main Results 

Public Tests Help on MBPP+ but Not Uniformly 

Table 1 reports the main pass rates. MBPP+ shows the clear-est TDD-style benefit: adding public tests improves hidden-test pass rate from 63.8% to 71.2%. Shuffled tests also help, but less than relevant tests, while irrelevant tests strongly hurt performance. This pattern suggests that MBPP+ contains tasks where public tests provide useful semantic guidance. HumanEval+ behaves differently. The model already solves 78.0% of tasks under NL-only prompting, and NL+tests does not improve hidden-test pass rate. Shuffled tests are slightly higher, suggesting that small fluctuations and prompt formatting may dominate the effect of public tests on this saturated dataset. LiveCodeBench v6-new is the hardest setting. NL-only pass@1 is only 13.1%, and NL+tests improves it to just 14.9%. Irrelevant tests reach 15.4%, slightly higher than rel-evant tests. This result cautions against interpreting all test-induced gains as semantic test utilization, especially when the base model has low capability on the task distribution. Qwen3.6-27B substantially raises LiveCodeBench NL-only pass@1 to 39.4%. However, original relevant tests reach only 42.3%, while shuffled tests reach 44.6% and irrelevant tests remain near baseline at 38.9%. The relevant-test change corresponds to 17 gains and 12 losses ( p = .458 ), so greater model capability does not turn the small aggregate increase into reliable evidence of semantic test use. 

Behavior Flips Reveal Small and Unstable Gains 

Behavior flips make these aggregate trends more concrete. On MBPP+, NL+tests produces 44 gains and 16 losses rel-ative to NL-only, for a net gain of +28 tasks. Shuffled tests produce a smaller net gain of +20, and irrelevant tests pro-duce a large net loss of -75. Thus, the MBPP+ improvement is not just a uniform prompt-length effect: relevant tests rescue many tasks that NL-only fails. On HumanEval+, NL+tests has 8 gains and 8 losses, for no net improvement. On LiveCodeBench v6-new, Qwen2.5-Coder original public tests yield only +3 net tasks over NL-only, while irrelevant tests yield +4. This is consistent with a low-capability regime in which extra examples or test-like text can perturb the model, but do not reliably guide it to the correct algorithm. Qwen3.6 produces more behavior flips but retains the same instability: original tests give +5 net tasks, shuffled tests give +9, and synthetic high5 tests give +3; none is significant. 

Relevant Tests Rarely Beat Matched Controls Directly 

Direct paired comparisons sharpen the distinction between semantic guidance and test-like context. As shown in Fig-ure 2(a), relevant MBPP+ tests exceed shuffled-output tests by only 2.1 points (15 versus 7 discordant tasks; 95% CI 

[−0.4, 4.8] ; p = .134 ), but exceed irrelevant tests by 27.2 points (95% CI [22 .2, 32 .3] ; p < . 001 ). Only the latter com-parison survives Holm correction across the eight original-test contrasts. On HumanEval+, relevant tests trail shuffled tests by 1.2 points and exceed irrelevant tests by 7.3 points; the latter is significant before correction ( p = .008 ) but not after it ( pHolm = .053 ). All direct LiveCodeBench contrasts span zero for both checkpoints, with effects from −2.3 to 

+3 .4 points. Thus, relevant tests clearly outperform unrelated context on MBPP+, but they do not show a reliable advantage over the more closely matched shuffled-output control. Figure 2(b) stratifies the original LiveCodeBench compar-ison by difficulty. For Qwen2.5-Coder, relevant tests change pass@1 by +9 .3, −1.9, and 0.0 points on easy, medium, and hard tasks. For Qwen3.6, the corresponding changes are 

+2 .3, +3 .8, and +2 .5 points. Every interval includes zero and no stratum survives Holm correction. The 7B direction is consistent with tests helping mainly where baseline capa-bility is sufficient, but the stratified evidence is too uncertain to establish a capability-by-test interaction. 

## Ablations: What Part of a Test Matters? 

Table 3 compares NL+tests with assertion-only and test-names-only controls. On MBPP+, assertion-only prompts reach only 54.8%, far below NL+tests at 71.2%. On Hu-manEval+, assertion-only is even weaker, at 32.3%. In con-trast, test-names-only is close to NL-only on both datasets. These controls suggest that tests do not simply replace the natural-language specification. The useful signal appears to come from combining the problem statement with concrete input-output behavior. 

## Synthetic Tests: Quantity, Quality, and Difficulty 

Synthetic Tests on MBPP+ and HumanEval+ 

Synthetic tests let us separate the effect of the original pub-lic tests from the broader question of test quantity and se-lection. On MBPP+, increasing high-scoring synthetic tests from one to two improves performance from 65.9% to 68.3%, but adding a third high-scoring test does not improve further. However, our heuristic quality score does not perfectly pre-dict usefulness: low-scoring and random three-test selections reach 71.4% and 71.2%, respectively, matching or exceed-ing high3. This indicates that surface-level test complexity is an imperfect proxy for tests that constrain common wrong implementations. HumanEval+ again shows saturation. Synthetic high3 and diverse3 match NL-only at 78.0%, while high1 and high2 are slightly lower. This dataset provides limited room for test-driven improvement with the evaluated model. 

Stress-Testing LiveCodeBench with Stronger Public Tests 

One possible explanation for the weak LiveCodeBench gains is that the original public tests are not strong enough. We therefore generate stronger public tests with a larger API model and construct high3 and high5 variants. After filtering and fallback, 118 of 175 tasks have at least five valid synthetic tests, with broad coverage across easy, medium, and hard problems. Table 5 shows that stronger and more numerous synthetic tests do not improve either Qwen checkpoint reliably on Live-CodeBench. For Qwen2.5-Coder, original NL+tests solves 26 tasks. Synthetic high3 and high5 each solve only 25 tasks. On the 118-task subset with at least five valid syn-thetic tests, original NL+tests solves 24 tasks, while syn-thetic high5 solves 23. Irrelevant tests remain comparable or stronger. For Qwen3.6, original tests improve from 69 to 74 solved tasks within their run, while synthetic high5 improves from 73 to 76 within its matched run. The corresponding net gains are only +5 ( p = .458 ) and +3 ( p = .701 ). Thus, the LiveCodeBench result is not merely caused by weak public examples; even with the stronger checkpoint, additional tests do not reliably translate into correct algorithms. ## Representation Analysis 

Prompt Condition Is Decodable 

Linear probes show that prompt condition is strongly en-coded in hidden states. On MBPP+, a condition probe reaches 82.5% accuracy and 0.953 AUC at the best layers. On Hu-manEval+, it reaches 87.7% accuracy and 0.972 AUC. By contrast, success probes are weaker: the best MBPP+ success probe reaches 68.5% accuracy and 0.723 AUC, while Hu-manEval+ success probing is near majority-class behavior. Qwen3.6 shows the same separation on LiveCodeBench. Its four-way condition probe reaches 86.7% accuracy and 0.964 macro-AUC, whereas the success probe reaches 67.7% accu-racy and 0.727 AUC. The rescue probe reaches a best AUC of 0.708, but has only 17 positive examples; its best accuracy equals the 84.0% majority baseline and is not informative. This supports a key distinction: hidden states clearly en-code that a prompt contains tests, but this does not mean the model has used those tests effectively. Figure 3 summa-rizes the separation across datasets. The rescue maxima vary substantially and should be interpreted cautiously because the positive class contains only 44, 8, and 17 examples on MBPP+, HumanEval+, and LiveCodeBench. 

More Tests Shift Hidden States More 

Table 6 summarizes layer-wise hidden-state shifts. On MBPP+, synthetic high1, high2, and high3 produce increas-ing average cosine distances: 0.0234, 0.0262, and 0.0289. The same monotonic trend appears on LiveCodeBench, where high5 shifts more than high3. However, the behav-ioral gains saturate or disappear. In LiveCodeBench, syn-thetic high5 shifts hidden states more than high3 but solves no additional tasks. For Qwen3.6, synthetic high5 increases the NL+tests average shift from 0.0185 to 0.0236 (about 28%), while the within-run behavioral net gain decreases from +5 to +3 tasks. The strongest counterexample is assertion-only prompt-ing. On MBPP+, synthetic high3 assertion-only prompts have a larger average shift than NL+tests, yet their pass rate is much lower. Similarly, irrelevant tests on LiveCodeBench produce the largest hidden-state shifts while matching or ex-ceeding relevant tests in pass@1. Shift Tracks Behavioral Change More Than Benefit 

Condition-level averages can hide whether representation shift is associated with useful task-level changes. Figure 2(c) therefore groups tasks by their paired behavioral outcome across the original-test runs. After controlling for added prompt characters, rescued tasks have 0.21 standard devi-ations more shift than stable failures (95% bootstrap CI 

[0 .01 , 0.42] ). However, harmed tasks have 0.51 standard devi-ations more shift than stable successes (95% CI [0 .32 , 0.70] ). Shift magnitude is therefore associated with behavioral change in both directions and more strongly with harmful flips than with rescues. This task-level result reinforces that prompt influence is not a directional measure of effective test utilization. 

## Discussion 

Test usefulness appears capability-dependent. MBPP+ contains many tasks where Qwen can use tests to choose or refine an implementation. LiveCodeBench v6-new con-tains many tasks for which the model lacks the algorithmic capability to solve the problem even when more tests are available. In this regime, tests can change the prompt rep-resentation without enabling correct reasoning. Scaling to Qwen3.6 substantially improves baseline capability, but rel-evant tests still do not outperform shuffled controls reliably. The difficulty-stratified estimates are compatible with capa-bility acting as a gate, but their intervals are wide and do not establish an interaction. Capability is therefore a plausi-ble necessary condition, but clearly not a sufficient one, for dependable test utilization. 

Representational perturbation is not semantic utiliza-tion. Our controls repeatedly separate these concepts. Irrele-vant and assertion-only prompts can induce large hidden-state changes. Yet those changes may not improve cor-rectness, and sometimes coincide with worse performance. Therefore, analyses of test-driven prompting should measure both behavior and representation. 

Heuristic test quality is fragile. Our synthetic MBPP+ experiments show that high-scoring tests under a simple com-plexity heuristic do not always produce the largest gains. A useful public test is not merely complex; it should rule out plausible wrong programs. Future work should incorporate mutation-based or model-based estimates of fault detection strength when selecting tests. 

## Related Work 

LLM code generation has been widely studied with bench-marks such as HumanEval and MBPP (Chen et al. 2021; Austin et al. 2021). EvalPlus strengthens evaluation by adding more rigorous private tests and showing that bench-mark pass rates can overestimate correctness (Liu et al. 2023). LiveCodeBench provides a continuously updated and contamination-aware benchmark over recent programming contest problems (Jain et al. 2024). Tests have also been used as inference-time signals rather than only as final evaluators. CodeRL uses example tests and critic feedback to regenerate programs, CodeT generates tests for candidate selection, and LEVER learns execution-based verifiers (Le et al. 2022; Chen et al. 2023; Ni et al. 2023). Self-debugging and execution-guided methods use runtime behavior to revise or guide code generation (Chen et al. 2024; Lavon, Katz, and Wolf 2025), while subsequent work identifies bias and failure modes in self-generated tests (Chen et al. 2025). Test-driven and test-aware code generation has received growing attention. Prior work reports gains from placing tests in prompts and formalizing user intent as tests (Math-ews and Nagappan 2024; Fakhoury et al. 2024). Multi-agent systems also assign separate roles to code generation, test design, and execution (Huang et al. 2023). Related TDD and BDD studies investigate executable behavior specifications, reliable self-generated tests with fine-grained feedback, and class-level test-driven synthesis (Liang et al. 2025a,b, 2026). Unlike these iterative generation or repair pipelines, our work uses one greedy completion per prompt and asks when sim-ply exposing public tests changes behavior and internal rep-resentations. Our representational analysis relates to work using hid-den states and probes to diagnose LLM behavior. We use probes and layer-wise shifts not as standalone explanations, but as diagnostics paired with per-task behavioral flips. This combination helps distinguish test-context sensitivity from effective test utilization. 

## Limitations 

Our experiments use two checkpoints from the Qwen fam-ily, so the results may not generalize to other model families or proprietary systems. Second, synthetic LiveCodeBench tests are generated without reference solutions, so their ex-pected outputs may contain oracle noise. We mitigate this by using them only as prompt context and evaluating on the original official tests, but generated tests may still mislead the model. Third, hidden-state shift and probing analyses are cor-relational. They show how prompts change representations, but do not identify a causal mechanism inside the model. Fourth, we evaluate one greedy completion per condition. The Qwen3.6 original and synthetic runs have matching NL-only prompt hashes but only 44 of 175 identical completions; their nonsignificant four-task difference ( p = .481 ) indicates run-level nondeterminism. We therefore restrict comparisons within runs and do not attribute cross-run raw differences to synthetic-test effects. Finally, our test-quality heuristic is lightweight; stronger mutation-based test selection may bet-ter predict downstream usefulness. The difficulty-stratified and task-level shift analyses are post hoc and should be in-terpreted as exploratory rather than causal. 

## Conclusion 

We studied whether code language models use public tests in test-driven prompting. Tests substantially improve MBPP+, have little effect on saturated HumanEval+, and yield un-stable gains on recent LiveCodeBench tasks. Synthetic tests and hidden-state analyses show that larger shifts need not improve correctness. With Qwen3.6, relevant and synthetic tests still yield small, uncertain gains while prompt condition remains more decodable than success or rescue. Test-driven prompting helps when the model can exploit test constraints; otherwise, tests may be prompt-context perturbations. References
