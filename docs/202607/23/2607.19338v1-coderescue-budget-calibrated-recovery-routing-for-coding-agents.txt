Abstract 

Coding agents increasingly operate in executable environments where a failed attempt produces actionable feedback rather than merely an incorrect answer. Existing cost-aware systems typically treat such failures as cascade decisions: try a cheap model first, then escalate hard cases to a stronger and more expensive model. In coding, however, execution feedback can also make further cheap-model recovery worthwhile, raising a budgeted de-ployment question: when should an agent spend more cheap compute, and when should it escalate? We formulate this post-failure decision as recovery routing over heterogeneous actions and train a supervised router from exe-cution rollouts. To make the same router usable under changing budgets, we add a Conformal Risk Control (CRC) layer that selects a deployment-time cost penalty without retraining and provides marginal expected-cost control under exchangeability. Across held-out failures from five coding benchmarks, cheap recovery and escalation exhibit complementary success patterns. The calibrated frontier improves over fixed actions, prompt-only routers, and a binary cascade baseline; in the main GPT-5.4-NANO /GPT-5.4 setting, one CRC-calibrated frontier point exceeds always-escalate 

solve rate while using 35% of its mean recovery cost. Code is available at

Recent work has moved code generation beyond isolated programming problems toward software-engineering agents that inspect repositories, edit files, execute commands, run tests, and iterate on failures (Jimenez et al., 2024; Yang et al., 2024; Jain et al., 2024; Wang et al., 2025; Pan et al., 2025; Ye et al., 2026). This shift is also visible in frontier-model reports, where coding capability is increasingly evaluated through repository-level patch generation, terminal use, sandboxed execution, and long-horizon agentic workflows (OpenAI, 2025b;a; Anthropic, 2025a; Google DeepMind, 2025). As coding agents become interactive systems rather than one-shot generators, inference is no longer a single model call. Each failed attempt creates a new decision point: should the agent repair the existing solution using execution feedback, start over with a different plan, or invoke a stronger model? Consider a developer asking an agent to implement a parser. A cheap model may produce code that fails a hidden boundary-case test. One reasonable response is to patch the existing logic using the error feedback; another is to discard the brittle strategy and generate a fresh implementation; a third is to call a stronger model if the failure suggests a deeper algorithmic issue. These responses have different costs, and the cheapest useful next step depends on the instance. Cost-aware LLM inference has therefore been studied through routing and cascading. Routers assign each query to a weak or strong model before generation, while cascades try a cheap model first and defer uncertain cases to a stronger model (Chen et al., 2024a; Ding et al., 2024; Ong et al., 2025; Dekoninck et al., 2025; Valkanas et al., 2025). These abstractions are powerful, but they often treat a weak model’s failure primarily as evidence that more capable model parameters are needed. This can leave useful cheap-model capacity on the table. Recent work on test-time scaling suggests a broader view: for many reasoning tasks, allocating more inference-time computation to the same model can be competitive with switching to a larger model (Snell et al., 2025). Coding agents make this distinction especially concrete because failed execution is itself informative. A compiler error, failed assertion, wrong output, timeout, or rejected patch can turn an underspecified programming problem into a diagnosed repair problem. In such cases, spending another cheap call with the right feedback may exploit the small model more effectively than immediately escalating. Thus the relevant decision is not only which model to call, but which recovery action to take. This motivates a recovery-action view of coding-agent inference. Production coding agents such as Claude Code and Codex expose the broader interaction pattern: they read codebases, edit files, run commands or tests, and continue from tool feedback (Anthropic, 2025b; OpenAI, 2025a). We instantiate this idea with a three-action post-failure router. After a cheap model fails, the router observes the problem statement, execution verdict, and stderr trace, then chooses among reflect (revise using feedback), replan (solve again with the cheap model from a fresh plan), and escalate (defer to a stronger model). We choose these actions as a minimal first-order recovery set rather than an exhaustive taxonomy of agent interventions. They span three common post-failure hypotheses: the current trajectory may be locally repairable using execution feedback, the trajectory may be wrong but the cheap model may still succeed from a fresh plan, or the failure may reflect a capability gap requiring a stronger model. Prior work supports each axis: feedback-driven code repair and iterative reflection motivate reflect (Shinn et al., 2023; Chen et al., 2024b; Zhong et al., 2024; Li et al., 2025); test-time compute scaling and repeated sampling motivate replan (Snell et al., 2025; Brown et al., 2024); and cost-aware routing and cascading motivate escalate (Chen et al., 2024a; Ding et al., 2024; Ong et al., 2025; Valkanas et al., 2025). Our successful-action analysis suggests that these actions are not strictly ordered: reflect and replan are much cheaper than escalate , but they are not uniformly worse; some examples are solved by cheap recovery actions, some require escalation, and some are not solved by any available action. We train the router from execution rollouts by labeling each example with the cheapest successful recovery action, and evaluate decisions by solve rate rather than plain classification accuracy because multiple actions may solve the same task. Beyond choosing the right recovery action, deployment adds another challenge: the desired cost-quality trade-off may change across users, workloads, and operating budgets. Some budget-aware routing methods optimize policies with a budget or cost target built into the training objective or constrained optimization problem (Zhang et al., 2026). Separately, con-formal cascade methods show that calibration can provide deployment-time guarantees, but 2Preprint. Under review. they typically calibrate scalar thresholds for accept/defer or stop/escalate decisions (Jung et al., 2025; Valkanas et al., 2025). Our setting requires budget control over heterogeneous recovery actions whose success patterns are non-monotone. We address this by placing a Conformal Risk Control (CRC) layer on top of a single trained router (Angelopoulos et al., 2024). CRC calibrates a deployment-time cost penalty that shifts the router from uncon-strained argmax toward cheaper actions, yielding marginal expected-cost control under exchangeability without retraining the router for each budget. Importantly, the guarantee concerns cost rather than solve rate, so the recovery actions can have non-monotone success patterns. The result is a discrete, budget-controllable frontier: tighter budgets select cheaper recovery behavior, while looser budgets permit more aggressive use of escalation. This paper makes three key technical contributions: • Post-failure recovery routing. We formulate coding-agent recovery as routing over 

reflect , replan , and escalate actions after execution feedback is observed. • Budget-controllable deployment. We add a CRC-calibrated cost knob that pro-duces multiple budgeted operating points from one trained router with marginal expected-cost control, without retraining for each budget. • Empirical recovery trade-offs. We provide empirical evidence on held-out coding-agent failures that cheap recovery and model escalation can be complementary, yielding a discrete cost–quality frontier. 

2 Related Work 

Cost-aware routing, cascading, and orchestration. Cost-aware LLM inference studies how to spend expensive model calls only when they are useful. Early and recent systems approach this either by routing inputs before generation or by cascading through models at inference time. FrugalGPT (Chen et al., 2024a) learns cascades over multiple LLM APIs, while HybridLLM (Ding et al., 2024) and RouteLLM (Ong et al., 2025) train pre-inference routers that choose between weaker and stronger models from the input query. AutoMix (Aggarwal et al., 2024) routes to larger models after an initial small-model answer using approximate self-verification, and Cascade Routing (Dekoninck et al., 2025) unifies routing and cascading. C3PO (Valkanas et al., 2025) adds explicit cost constraints to model cascades, while RACER (Zhang et al., 2026) optimizes a robust budget-aware router between reasoning and non-reasoning judges. These methods establish the importance of adaptive compute allocation, but their decisions are typically about which model, judge, or tool to invoke. Moreover, in budget-aware optimization approaches such as RACER, the budget enters the policy-learning objective; changing the deployment budget generally requires rerunning the optimization. In our setting, the recovery router is trained once; after one calibration pass, changing budgets only requires re-scanning a stored cost-penalty table. 

Coding agents, execution feedback, and iterative recovery. Recent coding-agent work shifts code generation from single-shot prediction to executable software-engineering en-vironments. SWE-bench (Jimenez et al., 2024) evaluates agents on real repository issues with test-based validation, and SWE-agent (Yang et al., 2024) shows that an agent-computer interface can let language models inspect files, edit code, and run commands. R2E (Jain et al., 2024), OpenHands (Wang et al., 2025), SWE-Gym (Pan et al., 2025), and Agents’ Last Exam (Sun et al., 2026) broaden this direction through executable environments, open agent platforms, training data, and long-horizon coding-tool tasks. Across these systems, execution feedback becomes a first-class signal: compiler errors, failed tests, wrong outputs, and timeouts can turn a failed attempt into a repair problem rather than merely a failed answer. Feedback-driven code repair methods such as Self-Debugging (Chen et al., 2024b) and LDB (Zhong et al., 2024) show how execution information can support local debugging, while iterative-improvement methods such as Self-Refine (Madaan et al., 2023) and Reflexion (Shinn et al., 2023) demonstrate the broader value of revision from feedback. A separate inference-scaling line shows that the same model can gain coverage from additional attempts: test-time compute scaling (Snell et al., 2025) and repeated sampling (Brown et al., 3Preprint. Under review. 2024) motivate fresh cheap-model replanning as an alternative to immediate escalation. These works motivate spending more computation after failure, but they do not decide which recovery mode is worth its cost. We study this budgeted choice directly: when to spend cheap compute on feedback-driven repair or replanning, and when to escalate to a stronger model. 

Conformal and selective deployment guarantees. Conformal methods provide a way to turn a held-out calibration set into deployment-time statistical guarantees. Conformal Risk Control (CRC) (Angelopoulos et al., 2024) extends conformal calibration beyond prediction-set coverage to bounded risks, making it a natural tool for controlling quantities such as error, abstention, or cost. In LLM systems, Trust or Escalate (Jung et al., 2025) uses conformal calibration to decide when a weaker judge can be trusted and when to escalate, while C3PO (Valkanas et al., 2025) is closest to our calibration goal in applying conformal tools to cost-constrained LLM cascades. The distinction is in the calibrated decision space: these methods largely operate along an ordered trust/escalate or stop/escalate path, whereas we calibrate a cost-regularized policy over heterogeneous post-failure recovery actions. Our guarantee is therefore a mean-cost guarantee for the recovery router, not a claim that the actions form a monotone cascade or that solve rate is conformally controlled. 

3 Method 

3.1 Problem Setup 

We study post-failure recovery routing for code generation. A cheap base model first attempts a programming task, and the generated code is executed by the evaluation environ-ment. We condition on cases where this initial attempt fails; all expectations in this section are over this conditional distribution of failed initial attempts. For each failed instance, the router observes a recovery context 

x = ( q, v0, e0),where q is the problem statement, v0 ∈ V is the execution verdict (e.g., wrong answer, timeout, or compile error), and e0 is the stderr trace. The router then chooses one recovery action from 

A = {reflect , replan , escalate }.The actions differ in their instruction and model: reflect asks the cheap model to use the execution feedback for a local repair; replan asks the cheap model to generate a fresh solution from a different plan; and escalate sends the problem and execution feedback to a stronger model. The verdict and stderr trace provide the router with a compact post-failure signal without requiring the failed code itself as input. These actions are interventions rather than mutually exclusive failure labels. The router is not asked to diagnose the true cause of failure; it chooses which additional computation to spend under a budget. Each action a ∈ A has an associated deployment cost estimate c(a, x) > 0 available to the router and calibrator, priced from the tokens consumed or expected for that action under model-specific input and output rates. Let S(x) ⊆ A denote the set of actions that solve instance x. A deployment policy π : X → A succeeds on x if π(x) ∈ S(x) and incurs cost 

c(π(x), x). The ideal budgeted recovery problem is max  

> π

E [1{π(X) ∈ S(X)}] s.t. E[c(π(X), X)] ≤ B,where B is a user-specified mean recovery budget. Unlike a standard model cascade, the action set is not assumed to form an ordered ladder of increasing capability: S(x) need not be monotone with action cost, and some failures may remain unsolved by any available action. The cheapest-successful label is a practical proxy for training a single-action router; it should not be interpreted as a calibrated estimate of the probability that each action succeeds. The router is a supervised fine-tuned language model. Given recovery context x, it scores each action by the average log-probability of its label tokens under the model, then normal-izes via softmax over A. Let sθ (a | x) ∈ (0, 1 ) denote this normalized probability for action 

a. The unconstrained router chooses π0(x) = arg max a sθ (a | x), which provides a single operating point on the cost–quality frontier.

Router training. We instantiate the recovery router with Q WEN 3.5-4B (Qwen Team, 2026) and fine-tune it as a three-way action scorer. Each router input consists of a compact metadata header—source, difficulty, and algorithm tag—followed by the problem statement, the execution verdict, and the stderr trace. The metadata supplies coarse distributional cues that are often absent from execution feedback alone, especially for wrong-output failures. The model is trained with full-parameter supervised fine-tuning; in our runs, we train for two epochs with learning rate 10 −5, cosine decay, and 10% warmup. At inference time, we score the labels by their average token log-probabilities and normalize the three scores with a softmax. Section 5.2.3 ablates the data recipes and backbone choices that led to this configuration. 

Evaluation protocol. Our primary metric is solve rate : the fraction of test examples for which the router’s chosen action lies in S(x). Unlike classification accuracy, solve rate credits any successful action, reflecting the fact that multiple actions may solve the same instance. Cost is measured as the mean per-example USD billed by the API for the chosen recovery action and reported in millidollars (m$); Appendix B.2 gives the action-cost details. For each target budget B, we select the CRC penalty bλ on the 360-example calibration split using the procedure in Section 3.4. We then freeze bλ and report solve rate and realized mean cost on the disjoint 360-example test split. The calibration split is used only to choose the operating point; all reported solve rates and costs are measured on held-out test problems.

5.2.2 Main Result: Budget-Controllable Frontier 

We next compare CRC-calibrated recovery routing against the baselines above and a binary cascade baseline. The binary cascade represents the standard two-way defer setting in our post-failure context: a scalar threshold decides whether to use cheap recovery or 

escalate . This instantiates the binary cheap/strong cascade structure used by systems such as FrugalGPT (Chen et al., 2024a) and the cost-controlled cascade setting of C3PO (Valkanas et al., 2025). Figure 3 shows that one trained router can be turned into a family of budgeted operating points. As the budget is relaxed, CRC moves the same router from cheap recovery be-havior toward more frequent escalation, tracing a discrete cost–solve-rate frontier without retraining. The frontier starts at 0.486 solve rate and 1.43 m$ per example, already above always-replan (0.453 at 1.59 m$), and reaches 0.817 at the unconstrained argmax point (5.51 m$). The most cost-effective gains occur at low and medium budgets. Around 2.56 m$, the three-action router reaches 0.717 solve rate, exceeding both the binary cascade at comparable cost (0.636) and always-escalate (0.686) while using only 35% of the always-escalate cost. Beyond this region, additional spending yields smaller marginal improvements: increasing mean cost from 2.56 to 5.51 m$ raises solve rate from 0.717 to 0.817, and the binary cascade becomes competitive near its high-cost peak. 5.2.3 Router Ablations and Cross-Model Check 

The quality of the learned router determines the attainable frontier, so we also ablate the training recipe in Table 2. The most important data choice is the metadata prefix: with hard cheapest-action labels, adding metadata improves solve rate from 0.656 to 0.697. Soft labels via weighted rollout copies do not improve the final router in this setting. On the model side, Qwen3.5-4B is the strongest backbone we tried; full fine-tuning is slightly better than LoRA on Qwen3.5-4B and more clearly beneficial on Qwen3-4B. We therefore use the Qwen3.5-4B full fine-tune with hard labels and metadata as the primary router. To check that the result is not specific to the GPT model pair, we also repeat the recovery-routing pipeline with a G EMINI -2.5-F LASH /G EMINI -2.5-P RO pair; the setup and results are reported in Appendix C. 

6 Conclusion 

We studied budget-controllable recovery routing for coding agents. Instead of treating a failed cheap-model attempt as a binary defer decision, we formulate recovery as a choice among heterogeneous actions. This formulation matches a central property of executable coding environments: failures provide diagnostic feedback, and the cheapest useful next step is not always the strongest model. Our results provide evidence that cheap recovery and model escalation can be comple-mentary on held-out coding failures, and that a learned recovery router can outperform 10 Preprint. Under review. fixed-action and prompt-only routing baselines. Adding a CRC calibration layer turns the same trained router into a family of budgeted operating points with marginal expected-cost control, allowing deployment budgets to change without retraining the router. The study also has clear limitations. We model recovery as a single post-failure decision, while deployed coding agents often recover over multiple rounds. The cheapest-successful training label is a useful proxy rather than a calibrated estimate of each action’s success probability. CRC controls expected recovery cost rather than solve rate, so quality improve-ments remain empirical. Future work should extend recovery routing to multi-step agent trajectories and richer deployment constraints.

C Cross-Model Generalization: Gemini 

The main experiments use the GPT-5.4-NANO /GPT-5.4 model pair. The action space is unchanged: reflect and replan reuse the cheap model with execution feedback, while escalate calls the strong model. 

Setup. We use 683 Gemini recovery examples for router training, with a disjoint holdout of 227 calibration and 229 test examples.
