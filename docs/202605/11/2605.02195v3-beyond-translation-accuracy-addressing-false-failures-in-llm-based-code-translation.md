## 摘要
大型语言模型（LLMs）在自动化代码翻译方面取得了显著成果。以往的研究主要通过高级提示和迭代修复来提高翻译的准确性，而对底层评估框架可靠性的关注相对有限。本文指出，代码翻译中报告的大量失败并非源于逻辑错误，而是由于评估过程引入的错误，例如不当的编译标志、缺少的库链接以及未配置的运行环境所致。我们在五种编程语言（C、C++、Java、Python、Go）和三个基准（Avatar、CodeNet、EvalPlus）上进行了大规模实证研究，涵盖了由 GPT-4o、DeepSeek-Coder 和 Magicoder 生成的 6,164 个翻译结果。我们的分析识别并分类了常见的“假阴性”问题，区分了会影响任何模型的管线诱发型失败与随 LLM 不同而变化的模型相关行为。研究结果强调了建立透明、配置感知的评估标准的必要性，以便更准确地衡量基于 LLM 的代码翻译的进展。

## Abstract
Large Language Models (LLMs) have achieved remarkable success in automated code translation. While prior work has focused on improving translation accuracy through advanced prompting and iterative repair, the reliability of the underlying evaluation frameworks has received less attention. In this paper, we demonstrate that a significant number of reported failures in code translation are not due to incorrect logic, but rather evaluation-induced errors stemming from improper compilation flags, missing library links, and unconfigured runtime environments. We conduct a large-scale empirical study across five programming languages (C, C++, Java, Python, Go) and three benchmarks (Avatar, CodeNet, EvalPlus), covering 6,164 translations generated by GPT-4o, DeepSeek-Coder, and Magicoder. Our analysis identifies and categorizes common false negatives, distinguishing pipeline-induced failures that affect any model from model-dependent behaviors that vary across LLMs. Our findings highlight the necessity for transparent, configuration-aware evaluation standards to accurately assess progress in LLM-based code translation.

- **研究动机**：现有的大型语言模型（LLMs）在代码翻译任务中取得显著进展，但评估方法普遍依赖于编译与测试通过率来判断正确性。这种评估框架默认运行环境完全准确，忽视了配置和编译参数的不一致。

## 二、方法论与分析框架

### 1. 核心思想
论文并非提出新的代码翻译算法，而是**构建一个分析管线（analysis pipeline）**，用于识别并分类“评估诱发的错误失败”。

### 2. 方法流程
该流程包含三个主要阶段：

1. **翻译生成阶段**：使用多个 LLM（GPT-4o、DeepSeek-Coder、Magicoder）将源程序翻译至目标语言。  
2. **自动评估阶段**：编译并运行翻译结果，记录编译错误、运行错误及测试失败情况。  
3. **诊断分析阶段**：保留代码不变，仅对编译及运行设置进行修复，若调整配置即可使测试通过，则认定为“评估诱发的错误”。

### 3. 错误分类策略
论文区分三类失败：
- **管线诱发型失败（Pipeline-Induced）**：由评估环境引起，与模型无关，如缺少库或编译标志。
- **模型相关型失败（Model-Dependent）**：与模型行为有关，如自然语言污染、主函数未调用等。
- **真正翻译错误（Genuine Translation Failures）**：跨语言语义差异导致的逻辑错误。

### 4. 自动修复思路
通过检测编译日志与运行输出，研究者采用**结构化人工检查**和**规则化配置修复**方式来确认错误根源，而非修改代码逻辑。

## 六、主要结论与发现

- 发现大量失败并非翻译逻辑错误，而是**评估系统引发的假阴性**。
- 主要错误类别：
  - **缺失库链接**（如 `-lm`, `-lssl`, `-lgmp` 等）
  - **语言特定编译规则冲突**：例如 Go 强制删除未用变量，导致翻译构建失败。
  - **测试套件转换错误**：如 PyTest → JUnit 时类型或断言不匹配导致误判。
  - **不合理超时设置**：不同语言执行效率差异导致错误判定。
- 明确区分了可修复的评估错误与真正的跨语言语义差异（如 API 不兼容、算子语义不同）。
- 强调应建立**配置感知（configuration-aware）评估标准**，以避免模型被不公平地惩罚。
