## 摘要
近年来，大型语言模型（LLMs）在标准基准测试上的自动程序修复任务中表现出强大的性能。然而，这些基准通常只在存在单一规范形式错误代码的情况下评估模型，无法反映真实软件中常见的语法多样性，从而使得鲁棒性问题基本未被考察。本文构建了 HEJ-Robust——一个基于 HumanEval-Java-Bug 并通过八种保持语义的代码变换生成的鲁棒性基准，总计包含 1,450 个变换后的实例。我们在该基准上评估了五个经过微调的 LLM，结果显示在多种代码变换下模型性能下降超过 50%，表明当前基于 LLM 的程序修复模型对细微的语法变化缺乏鲁棒性。

## Abstract
Recent Large Language Models (LLMs) have shown strong performance on automated program repair across standard benchmarks. However, these benchmarks evaluate models on a single canonical form of buggy code and do not reflect the syntactic variations commonly observed in real-world software, leaving robustness largely unexamined. In this work, we construct HEJ-Robust, a robustness benchmark built from HumanEval-Java-Bug using eight semantics-preserving code transformations, resulting in 1,450 transformed instances. We evaluate five fine-tuned LLMs on this benchmark and show that model performance drops by over 50% under several transformations, indicating that current LLM-based repair models lack robustness to minor syntactic variations.

## 一、研究背景与核心问题  

- **研究背景**：  
  自动程序修复（Automated Program Repair, APR）旨在自动生成修复错误代码的补丁。早期方法多采用“生成–验证”范式（如 GenProg、PAR），但存在扩展性差、易过拟合的问题。  
  随着代码预训练语言模型（如 PLBART、CodeT5）的发展，LLM 驱动的程序修复方法表现突出，能够将程序修复视为代码翻译问题：从“错误代码”生成“修复代码”。  

- **核心问题**：  
  现有 APR 基准（如 Defects4J、HumanEval-Java-Bug）通常以单一规范形式的错误代码为输入，缺乏对真实软件开发中**语法多样性与形式变异的考虑**。  
  这种设计无法衡量模型面对语义等价但语法不同的代码时是否能保持修复能力，即缺乏**鲁棒性评估**。  

- **研究动机**：  
  作者指出现有研究中虽已关注代码生成模型在语义保持变换下的脆弱性，但针对 LLM 级别的 **自动程序修复鲁棒性测试** 尚为空白，因此提出 HEJ-Robust 作为新基准。

## 二、方法论与基准设计  

### 1. 核心思想  
通过在 **HumanEval-Java-Bug** 数据集上施加八种语义保持的代码变换，生成结构与语法多样的变换样本，形成可执行的鲁棒性评估基准 **HEJ-Robust**。  

该基准允许系统性评估 LLM 程序修复能力在语法扰动下的稳定性。  

### 2. 数据集基础  
- 基准构建基于 **HumanEval-Java-Bug**（164 个人工注入错误的 Java 函数），每个实例包含：  
  - 错误代码  
  - 人工标注 bug 位置  
  - 人类修复补丁  
  - 可执行测试用例  

### 3. 八种语义保持变换  
共生成 **1,450 个变换实例**，涵盖真实开发中常见的语法变异类型：  

| 类型 | 说明 |
|------|------|
| (1) 局部变量重命名 | 对局部变量使用 LLM 生成的自然化新标识符 |
| (2) 方法重命名 | 与变量重命名策略相同 |
| (3) 参数重命名 | 对函数参数名称变化 |
| (4) 日志插入 | 在方法起始处加入 `System.out.println("log")` |
| (5) Try–Catch 插入 | 向代码插入防御性异常处理结构 |
| (6) 布尔交换 | 翻转布尔变量及相应逻辑使用 |
| (7) 循环结构交换 | `for ↔ while` 的语法结构变换 |
| (8) 条件重排 | `a == b → b == a` 等等价条件互换 |

### 4. 实现细节  
- **重命名策略**：采用 CodeBERT 与 GraphCodeBERT 的掩码预测机制生成具有上下文自然性的替代标识符，通过余弦相似度筛选合适替换方案。  
- **结构变换**：利用 JavaParser 工具与 JavaTransformer 库基于 AST 语法树实现变换。  
- 变换后手动重新标注 bug 位置，并由第二作者复查 10% 实例以控制标注一致性。

## 三、实验设计  

### 1. 模型设置  
在 HEJ-Robust 上评估 **5 个公开可用、已微调的 LLM 模型**（来自 Jiang et al., 2023）：  
- PLBART (base, large)  
- CodeT5 (small, base, large)  

### 2. 任务与指标  
- **任务**：根据 bug 源码生成修复补丁。  
- **主指标**：`Pass@10`（10 个候选中至少一个通过全部测试算修复成功）。  
- **辅助指标**：CodeBLEU（语法/语义相似度指标，仅作参考）。  

### 3. 实验方案  
- 每个模型在原始与变换版本的 HumanEval-Java-Bug 上分别评估。  
- 按八类变换结果独立呈现，比较每类变换前后性能差异。  
- 总计 8 类 × 5 模型 = 40 组主要实验，部分类型仅适用到少量样本（如 Boolean Exchange 仅 7 个）。

## 六、主要结论与发现  

1. **漏洞修复鲁棒性显著不足**：  
   多数模型在语义保持型代码变换后性能显著下降，尤其是：  
   - 局部变量重命名：Pass@10 平均下降 **50%~57%**。  
   - 尝试–捕获插入与条件重排等结构变换也引入 10%~30% 的降幅。  

2. **模型规模与鲁棒性无正相关**：  
   大模型（如 CodeT5_large）在某些变换下甚至比小模型更易退化。  

3. **指标可靠性差异**：  
   CodeBLEU 指标对变换几乎不敏感，不适合作为鲁棒性度量；  
   Pass@k（基于执行测试）更能准确反映真实修复结果。  

4. **轻微的语法扰动即可导致修复失败**，显示当前 LLM 在代码理解层面缺乏抽象化泛化能力。
