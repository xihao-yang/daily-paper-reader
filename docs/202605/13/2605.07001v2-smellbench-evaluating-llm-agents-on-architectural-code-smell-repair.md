## 摘要
架构性代码异味会削弱软件的可维护性，手动修复代价高昂。与局部化的缺陷不同，这类问题需要对设计意图进行跨模块推理，这对开发者和自动化工具而言都具有挑战性。尽管大型语言模型（LLM）代理在缺陷修复和代码级重构方面表现出色，但其在架构性代码异味修复中的能力尚未得到探索。本文首次对LLM代理在架构性代码异味修复上的表现进行了实证评估。我们提出了SmellBench，这是一种任务编排框架，结合了针对异味类型优化的提示（prompt）设计，并支持迭代的多步执行；同时，我们还提出了一种评分方法，分别评估修复有效性、误报识别以及对代码库整体质量的影响。我们在Python项目scikit-learn中，通过PyExamine检测到65个高严重等级的架构性异味，基于专家评审结果，评估了来自GPT、Claude、Gemini与Mistral四个模型家族的11种代理配置。专家验证表明，检测出的异味中有63.1%为误报，而表现最好的代理达到了47.7%的修复率。代理在误报识别任务中与专家的一致性最高可达$κ=0.94$，但修复激进度与整体代码质量呈反比关系：最激进的代理引入了140个新的异味。这些结果揭示了当前LLM在局部代码转换与跨模块重构所需的架构理解之间的差距。SmellBench为追踪自动化软件工程这一尚未深入研究的方向提供了可重用的基础设施。我们在https://doi.org/10.5281/zenodo.19247588公开了代码与数据。

## Abstract
Architectural code smells erode software maintainability and are costly to repair manually, yet unlike localized bugs, they require cross-module reasoning about design intent that challenges both developers and automated tools. While large language model agents excel at bug fixing and code-level refactoring, their ability to repair architectural code smells remains unexplored. We present the first empirical evaluation of LLM agents on architectural code smell repair. We contribute SmellBench, a task orchestration framework that incorporates smell-type-specific optimized prompts and supports iterative multi-step execution, together with a scoring methodology that separately evaluates repair effectiveness, false positive identification, and net codebase impact. We evaluate 11 agent configurations from four model families (GPT, Claude, Gemini, Mistral) on 65 hard-severity architectural smells detected by PyExamine in the Python project scikit-learn, validated against expert judgments. Expert validation reveals that 63.1% of detected smells are false positives, while the best agent achieves a 47.7% resolution rate. Agents identify false positives with up to $κ= 0.94$ expert agreement, but repair aggressiveness and net codebase quality are inversely related: the most aggressive agent introduces 140 new smells. These findings expose a gap between current LLM capabilities in localized code transformations and the architectural understanding needed for cross-module refactoring. SmellBench provides reusable infrastructure for tracking progress on this underexplored dimension of automated software engineering. We release our code and data at https://doi.org/10.5281/zenodo.19247588.

## 一、核心问题与研究背景

- **研究动机**  
  随着软件系统规模与复杂性的增长，其架构会逐步积累“结构退化”（architectural degradation），导致维护成本上升、开发效率下降。  
  常见的应对方式如人工代码评审和周期性重构，成本极高且依赖开发者对于系统设计意图的理解。

- **问题核心**  
  架构级代码异味（architectural code smells）涉及包、模块层面的设计缺陷，典型工具可检测这些模式，但经常存在**高误报率**，需人工甄别“设计选择”与“实际问题”。  
  当前大语言模型（LLM）虽已在**bug修复和方法级重构**上表现突出，但其在**跨模块、设计层面的推理与修复能力**尚未被系统评估。

- **研究意义**  
  该工作首次针对LLM智能体的架构异味修复进行实证评估，以揭示模型在从“语法修复”到“设计重构”转变中的能力缺口，并提供首个系统基准。

## 二、方法论：SmellBench 框架

### 1. 核心思想
提出 **SmellBench** —— 一个用于评估LLM代理架构级代码异味修复能力的任务编排与评分框架，特点：
- 按异味类型定制 **优化提示（prompt playbook）**
- 支持 **迭代多步骤修复流程**
- 采用 **多维度评分体系**，分评修复质量、误报识别、代码库净影响

### 2. 关键技术组成

- **任务编排机制（Task Orchestration）**
  - 基于 **Model Context Protocol (MCP)** 实现任务分配与结果记录：
    - `next_task`：获取待处理任务  
    - `mark_task`：记录执行结果  
    - `get_task_packet`：组装任务上下文信息（包括异味类型、检测报告、影响文件、few-shot示例等）
  - 每个任务包包含 smell 类型、对应执行剧本（playbook）、三种终止状态示例（Done / Accepted / Need More Work）。

- **任务生命周期（Lifecycle）**
  - 状态机驱动，防止死循环和不合规输出。  
  - 四个终止状态：
    - `Done`（修复完成）  
    - `Accepted`（识别为误报并回退改动）  
    - `Need More Work`（分步修复进行中）
    - `Blocked`（因外部约束无法执行）

- **Prompt 优化：GEPA机制**
  - 使用 GEPA（Reflective Prompt Evolution）自动优化每种异味类型的提示结构。
  - 结合两阶段评分：
    - **静态验证器**（30%权重）检查结构完整性、规则符合性；
    - **Judge模型**（70%权重）基于五维评价（目标对齐、执行质量、状态规范、示例质量、输出纪律）生成得分与反馈用于迭代改进。
  - 采用 **异构模型架构**：小模型生成、大模型评判与反思（如 GPT-5.1-mini + GPT-5.2）。

- **评分公式**  
  对每个任务定义得分 \( s \in [-1, 1] \)，依据修复效果或误判情况：  
  成功修复 → +1；部分改善 → (0,1)；误判或恶化 → < 0。  
  三类平均值按权重组合得总体指标：
  \[
  E = 0.60 \times TP + 0.20 \times FP + 0.20 \times Partial
  \]
  其中 TP 表示真实异味修复成效，FP 表误报识别能力。

## 三、实验设计

### 1. 数据与场景
- 目标项目：**scikit-learn v1.7.2**
  - 约 20 万行 Python 代码（不含测试）、100+模块。

- 异味检测工具：**PyExamine**  
  检测七种架构异味，最终选择五类实例量充足者：
  1. Scattered Functionality  
  2. Redundant Abstractions  
  3. Unstable Dependencies  
  4. Improper API Usage  
  5. God Object  

- 选择标准：仅保留 **“Hard”难度层级** (跨模块、核心包影响较大)，共 **65 个任务**。

### 2. 基准构成与验证
- 专家人工标注：
  - 41个误报（63.1%）、11个真异味（16.9%）、13个部分有效（20.0%）。

### 3. 对比方法
- 共评估 **11 种LLM代理配置**：
  - 四个家族：GPT（多版本）、Claude（Opus / Sonnet / Haiku）、Gemini（Pro / Flash Lite）及Mistral（Devstral）。
  - 另含一个无框架 baseline：Claude Haiku 4.5 最简提示。
- 使用各模型官方 CLI 版本，无额外强化推理或扩展设置。

## 六、主要结论与发现

1. **修复有效性（RQ1）**  
   - 最佳代理（GPT 5.3 Codex Spark）修复率达 **47.7%**（31/65）；
   - 其余四个模型形成 **27.7%修复下限**。
   - “Unstable Dependency” 最能区分模型能力（差异 0–7 个修复）。
   - Improper API Usage 无代理能修复（显示设计理解难度高）。

2. **误报识别（RQ2）**  
   - 准确度高，部分代理与专家一致性达 **κ=0.94**；
   - 七个代理实现零错误误报分类。

3. **模糊异味处理（RQ3）**  
   - 最有判别力的维度：GPT 5.3 Codex Spark处理效果最高（得分0.353）；
   - 多数代理倾向保守标记为误报，避免错误修复。

4. **代码库净影响（RQ4）**
   - 修复积极性与质量呈 **负相关**：  
     - GPT 5.3 Codex Spark 引入 140 个新异味（净差 −109），  
     - 保守代理如Gemini 3.1 Pro净改善 +16。

5. **排名稳健性（RQ5）**  
   - 三层性能梯度（顶级、中层、底层）稳健一致，不受权重影响。
