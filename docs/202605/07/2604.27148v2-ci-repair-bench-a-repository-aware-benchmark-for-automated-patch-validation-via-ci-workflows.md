## 摘要
持续集成（Continuous Integration，CI）通过多阶段工作流在代码库层面上强制保证正确性，是现代软件开发的核心环节。然而，对 CI 失败进行诊断和修复仍然是一项具有挑战性的任务。与传统的程序修复不同，CI 失败常常涉及非代码工件、环境与依赖问题、嘈杂的执行日志以及工作流级约束。现有的程序修复基准在这一场景下表现不足：它们主要以测试为中心，将修复限定在源代码层面，假设固定的执行环境，并在简化的 CI 工作流下进行评估，而这些与真实的代码库级验证不符。我们提出了 CI-Repair-Bench，这是一个面向 CI 验证的代码库级程序修复基准，基于真实的 GitHub Actions 执行构建而成。该基准包含来自 103 个代码库的 567 个 CI 失败实例，并通过在原始工作流下重新执行完整 CI 来独立评估修复的正确性。失败被划分为 12 种 CI 错误类型，从而实现细粒度、基于错误类型的评估。为了展示基准的使用，我们提供了一个参考 CI 修复工作流，用于分析 CI 日志定位故障并生成候选补丁。实证结果显示，自动修复在工具强制约束的定位型故障（如格式化和代码检查）中最为有效，而环境、依赖和配置相关的失败仍然具有挑战性；表现最好的大型语言模型实现了 18.9% 的修复成功率。CI-Repair-Bench 为推动 CI 原生自动程序修复研究提供了一个真实的评估基础。

## Abstract
Continuous Integration (CI) enforces repository-level correctness through multi-stage workflows and is central to modern software development, yet diagnosing and repairing CI failures remains challenging. Unlike traditional program repair, CI failures frequently involve non-code artifacts, environment and dependency issues, noisy execution logs, and workflow-level constraints. Existing program repair benchmarks fall short in this setting: they are largely test-centric, restrict repairs to source code, assume fixed execution environments, and evaluate under simplified CI workflows that do not reflect real repository-level validation. We introduce CI-Repair-Bench, a benchmark for CI-verified, repository-level program repair constructed from real GitHub Actions executions. It contains 567 CI failure instances from 103 repositories and evaluates repair correctness exclusively through full CI re-execution under original workflows. Failures are categorized into 12 CI error types, enabling fine-grained, error-type-aware evaluation. To demonstrate benchmark usage, we include a reference CI repair workflow that analyzes CI logs to localize faults and generate candidate patches. Empirical results show that automated repair is most effective for localized, tool-enforced failures such as formatting and linting, while environment, dependency, and configuration-related failures remain challenging; the best-performing LLM achieves an 18.9% repair success rate. CI-Repair-Bench provides a realistic evaluation foundation for advancing research on CI-native automated program repair.

## 二、方法论与技术流程

### 核心思想

- 提出 **CI-Repair-Bench**：一个仓库感知的自动程序修复基准，基于真实的 **GitHub Actions** 工作流构建。
- 修复验证不再仅仅通过单元或集成测试，而是以 **完整 CI 重执行** 为唯一正确性标准。

### 构建流程（概述）

1. **数据来源与收集**
   - 从 103 个活跃的开源 Python 仓库中收集 CI 执行日志。
   - 基于 **失败–成功提交对（failure–success commit pairs）**提取修复样本。
2. **数据过滤与清洗**
   - 排除与非代码验证无关的工作流（如部署、文档生成）。
   - 去除无法在公共环境中复现的或具有不稳定行为的 CI 实例。
3. **标准化与复现**
   - 保留验证相关步骤（环境设置、依赖安装、构建、静态分析、测试）。
   - 以统一触发事件重新执行，保证语义等价。
4. **标注与分类**
   - 每个实例标注为一个或多个 CI 错误类型（共 12 类，如格式错误、依赖冲突、配置错误等）。
5. **验证机制**
   - 对修复候选补丁执行完整 **GitHub Actions** 重运行。
   - 只有所有 CI 任务成功完成时才认定为有效修复。

### 参考修复框架（LLM 驱动）

三阶段流水线，构成自动化修复的评价原型：
1. **CI日志分析**：  
   - 将长日志分段（chunking）并以 LLM 形成结构化故障摘要，提取关键错误定位。
   - 使用“agent-based iterative”策略反复推理而非简单检索。
2. **故障定位**：  
   - 基于最近更改的文件筛选候选目标；利用 LLM 分析代码片段和日志上下文确定具体出错位置。
3. **补丁生成**：  
   - 对明确定位的代码区域执行最小修改。若错误由工具约束（如 lint、format）引起，优先用工具自动修复。
   - 生成的补丁须能在仓库环境成功应用且无冲突。

## 六、主要结论与发现

- **总体结果**
  - 修复成功率（Pass@1）在四个模型中分布：
    - GPT-5-mini：**18.9%**
    - DeepSeek-Coder：**15.9%**
    - DeepSeek-Chat：**13.2%**
    - GPT-4o-mini：**7.9%**
  - 即最佳模型仅能修复不到五分之一 CI 失败，表明任务难度高。

- **结构性发现**
  - 95% 以上补丁可正确应用，但近 80% 在 CI 验证阶段失败。
  - 日志分析方式影响显著：改用BM25检索后，成功率下降28%~75.9%。
  - 成功修复集中于 **格式与Lint** 等工具可检测的局部错误，而环境、依赖、配置类修复几乎无法完成（0~9%）。

- **总体结论**
  - 当前 LLM 对 CI 失败的自动修复仅在可局部定位问题上有效。
  - CI-Repair-Bench 提供了更真实的验证语义，使研究可聚焦于仓库级、环境感知的修复方法。
