## 摘要
开发者在实现相关功能的不同代码位置上经常会犯类似的错误。这些位置被称为 sibling（同类位置），它们存在相似的问题并需要相似的修复。准确识别 sibling 并保持一致地修复它们，对自动化程序修复至关重要。Hercules 是一种专门用于 sibling 修复的最先进技术。然而，它受到一些限制，包括对 sibling 位置及提交历史可用性的强假设、基于抽象语法树（AST）的僵化匹配方法，以及模板化补丁生成的灵活性不足。为解决这些问题，我们提出了 SiblingRepair，这是一种基于大语言模型 (LLM) 的新型多片段自动程序修复（APR）技术，专注于 sibling 修复。SiblingRepair 从通过谱系故障定位识别出的可疑位置出发，利用基于 token 和嵌入的代码匹配搜索语义相关的 sibling 候选，而不受限于失败测试覆盖率或提交历史。随后，它使用 LLM 来识别与失败相关的 sibling，并通过两种互补的策略生成一致的补丁：同步修复，即联合修复 sibling；以及迭代修复，即逐步分析候选以构建补丁。SiblingRepair 还保留了先前可疑位置生成的有前景补丁，并将它们组合成通用的多片段补丁。我们在 Defects4J 和 GHRB 基准集上评估了 SiblingRepair。结果表明，SiblingRepair 明显优于包括 Hercules 在内的现有多片段修复技术。我们的评估进一步验证了其修复效率、sibling 检测与修复组件的有效性，以及 LLM 数据泄漏对结果的有限影响。总体而言，SiblingRepair 推动了自动化 sibling 修复和通用多片段修复的进展。

## Abstract
Developers often make similar mistakes across code locations implementing related functionalities. These locations, called siblings, share similar issues and require similar fixes. Accurately identifying siblings and consistently repairing them are crucial for automated program repair. Hercules is a SOTA technique designed for sibling repair. However, it is limited by strong assumptions about sibling locations and commit-history availability, rigid AST-based sibling matching, and inflexible template-based patch generation. To address these limitations, we present SiblingRepair, a new LLM-based multi-hunk APR technique specialized for sibling repair. Starting from a suspicious location identified by spectrum-based fault localization, SiblingRepair searches for semantically related sibling candidates using token- and embedding-based code matching, without restricting discovery to failing-test coverage or commit history. It then uses an LLM to identify failure-relevant siblings and generate consistent patches through two complementary strategies: simultaneous repair, which jointly repairs siblings, and iterative repair, which progressively analyzes candidates for patch construction. SiblingRepair further preserves promising patches generated from earlier suspicious locations and combines them into generalized multi-hunk patches. We evaluate SiblingRepair on the Defects4J and GHRB benchmarks. The results show that SiblingRepair substantially outperforms SOTA multi-hunk repair techniques including Hercules. Our evaluation further demonstrates its repair efficiency, the effectiveness of its sibling detection and repair components, and limited impact of the LLM data leakage on the results. Overall, SiblingRepair advances automated sibling and general multi-hunk repair.

## 一、研究背景与核心问题

- **研究动机**  
  自动程序修复（Automated Program Repair, APR）旨在自动生成补丁以修复程序缺陷，从而减轻开发者负担。  
  然而，开发者往往在相似逻辑的多个位置犯下类似的错误，这些代码位置被称为 **sibling（同类）**。  
  - 约 14% 的多位置修复（multi-hunk fixes）属于 sibling 类型。  
  - 传统 APR 方法（如 **HERCULES**）在处理 sibling 修复时存在以下局限：
    1. **强假设依赖于失败测试覆盖和提交历史**，导致无法完整发现同类错误位置；
    2. **AST 结构匹配僵化**，遗漏语义相似但结构不同的错误位置；
    3. **模板式补丁生成缺乏灵活性**，且对 sibling 识别错误缺乏容错性。
- **核心问题**  
  如何在不依赖提交历史和严格结构匹配的前提下，**精确发现程序中存在语义关联的 sibling 代码片段，并生成一致的多位置补丁**。

## 二、方法论：SiblingRepair 的核心思想与关键技术

- **总体思路**  
  SiblingRepair 是一种 **基于大语言模型（LLM）的多片段自动程序修复技术**，通过两阶段流程实现：
  1. **候选 sibling 检测**：结合 token 与语义嵌入的匹配算法；
  2. **LLM 驱动的补丁生成**：采用 “同时修复”（Simultaneous Repair）与 “迭代修复”（Iterative Repair）两种策略。  
     
  该框架克服了 HERCULES 的三大限制，实现更加灵活和高召回率的 sibling 修复。

---

### 1. 候选 sibling 检测

由以下三步组成（对应算法 1 的前半部分）：

1. **上下文提取（Context Extraction）**  
   - 根据 reaching-definition 分析确定可疑语句的上下文（相关变量的定义）。
2. **Token 层相似过滤（TF-IDF）**  
   - 对所有被测试执行的语句进行分词和词频统计；
   - 计算 TF-IDF 相似度；
   - 选取前 100 个最相似的上下文作为初始候选。
3. **语义嵌入匹配（Embedding Matching）**  
   - 使用 OpenAI 的 `text-embedding-ada-002` 模型生成嵌入；
   - 依据余弦相似度筛选最终候选兄弟位置。  
   > 优势：既考虑词面相似度，又平衡效率与语义理解；不依赖 AST 或提交历史。

---

### 2. 同时修复（Simultaneous Repair）

- **目标**：在 LLM 的帮助下，同时识别失败相关的 sibling 并为其生成一致修复补丁。
- **关键机制**（算法 2）：
  - 候选过滤：基于 **Jaccard 相似度 α** 过滤低相似度的候选；
  - 将剩余候选按方法分组，生成修复上下文；
  - 通过 **构造多部分 Prompt**（见 Fig. 3）向 LLM 提供：
    - 方法代码与可疑位置；
    - 失败测试用例、堆栈跟踪；
    - 以往补丁与反馈；
    - 候选 sibling 与上下文；
    - 可用修复成分（fix ingredients，如相关字段或方法）。  
  - LLM 输出补丁 → 运行测试验证 → 若通过则保留为“plausible patch”；  
    未通过的补丁与测试结果作为反馈再次提示 LLM 精炼。
- **输出**：可行补丁 (plausible patch) 或作为后续迭代修复的参考。

---

### 3. 迭代修复（Iterative Repair）

- **动机**：解决同时修复阶段因 LLM 幻觉或过滤误差导致的失败。
- **思路**：
  - 按方法逐一处理候选 sibling；
  - 对每个方法独立尝试补丁生成，并评估是否有“修复进展”：
    - 若**减少失败测试**或**执行超出原异常点**，视为“promising patch”；
  - 将 promising patch 加入候选库，用于后续地点修复；
  - 可逐步组合成多片段补丁。
- **优势**：
  - 增强容错性与鲁棒性；
  - 可通过历史积累实现跨位置复用，支持通用 multi-hunk 修复。

## 三、实验设计

### 1. 数据与基准

- **主要数据集**
  - **Defects4J v1.2 / v2.0.1** ：经典 Java 缺陷集；

- **子集划分**
  - 单片段错误（Single-hunk）  
  - 多片段错误（Multi-hunk）  
  - 同类错误（Sibling，特殊类型的 Multi-hunk）

### 2. 对比方法

- **HERCULES**（AST 匹配 + 模板修复）
- **ARJACLM**（搜索式 + LLM 辅助）
- **ITER**（基于迭代学习的神经修复）
- **ThinkRepair**（仅在已知方法下比较）
- **其他未比较的工具原因**：
  - 或假设完美定位（PFL），或非测试驱动，或仅限单片段修复。

### 3. 实验设置

- **Fault Localization**：
  - 两种场景：
    - SBFL：使用谱系故障定位（Ochiai 指标）；

- **时间预算**：每个缺陷限制 5 小时。
- **Patch 评估**：人工比对开发者补丁，确认语义等价性。
