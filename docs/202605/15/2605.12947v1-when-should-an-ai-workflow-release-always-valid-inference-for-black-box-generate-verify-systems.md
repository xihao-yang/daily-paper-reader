## 摘要
近年来，借助大型语言模型（LLM）的人工智能工作流越来越多地通过生成—评估—修订的迭代循环来产生输出。每一次迭代都可能改进候选结果，但也同时带来一个发布决策：何时停止并输出当前结果？这带来了统计上的挑战，因为部署时的评估器得分是自适应生成并被反复监控的，而用于校准的似然模型或可交换性假设通常不可用。我们提出了一种可始终有效的发布封装器，可应用于现有的生成—评估管线。该封装器构建一个高分失败样本的硬负参考池，将部署时的评估器得分与该参考池进行校准，并使用 e-process 累积所得证据。这样分离了两个角色：参考池将黑箱分数转换为保守的证据，而 e-process 在可选停止条件下提供有效性。在理论上，我们表明保守的参考池可在有限样本条件下控制在不可行任务上发布的概率，也就是说，在工作流无法生成可靠解决方案的任务上。我们还刻画了在何种条件下相同的保守规则仍能在可行任务上实现有意义的发布。在 MBPP+ 编码代理的案例研究中，该封装器相较于基线停止规则，减少了过早且错误的发布，同时仍然能够在工作流持续积累中等支持证据的任务上完成发布。

## Abstract
LLM-enabled AI workflows increasingly produce outputs through iterative generate-evaluate-revise loops. Each iteration can improve the candidate, but it also creates a release decision: when to stop and output the current result? This raises a statistical challenge because deployment-time evaluator scores are adaptively generated and repeatedly monitored, yet the likelihood models or exchangeability assumptions typically used for calibration are unavailable. We propose an always-valid release wrapper for existing generator-evaluator pipelines. The wrapper builds a hard-negative reference pool of high-scoring failures, calibrates deployment-time evaluator scores against this pool, and accumulates the resulting evidence with an e-process. This separates two roles: the reference pool turns black-box scores into conservative evidence, while the e-process provides validity under optional stopping. In theory, we show that a conservative reference pool yields finite-sample control of the probability of releasing on infeasible tasks, that is, tasks for which the given workflow is not capable of producing a reliable solution. We also characterize conditions under which the same conservative rule still achieves nontrivial release on feasible tasks. In an MBPP+ coding-agent case study, the wrapper reduces premature incorrect release relative to baseline stopping rules while still releasing on tasks for which the workflow repeatedly accumulates moderate supporting evidence.

- **核心问题**：  
  由于评估分数是自适应生成、重复监测的，传统统计校准方法（基于似然模型或可交换性假设）不适用于 LLM 这种黑箱式的动态交互过程。简单的基于高分阈值的停止策略容易导致“p-hacking”式的错误发布，即在不可行任务上误判为成功。  
- **研究目标**：  
  构建一种**始终有效（always-valid）**的发布机制，在不知道模型分布的前提下，实现对错误发布概率的控制，同时保持在可行任务上的合理发布率。

## 2. 方法论：始终有效发布封装器（Always-Valid Release Wrapper）

### 2.1 核心思想

- 将黑箱的生成—验证工作流视为**序列统计推断问题**。
- 构建一个可与任何现有生成器和验证器配合的模块化“封装器”，无需重训练或分布建模。
- 关键目标是确保  
  \[
  P(D = 1 | F = 0) \leq \alpha
  \]
  即：在不可行任务上错误发布的概率受控于 α。

### 2.2 技术流程

1. **构建硬负样本参考池（Hard-Negative Reference Pool）**  
   - 离线阶段从辅助校准集生成一批错误但高分的样本（即高评分的失败案例），形成参考池 \(R = \{R_i\}\)。
   - 用于校准在线评估得分，使得分值更具保守性。

2. **参考池校准（Rank-based Calibration）**  
   - 在线阶段：将当前验证器得分 \(S_t\) 与参考池进行比较，计算经验p值：
     \[
     p_t = \frac{1 + \sum_{i=1}^n 1\{R_i \ge S_t\}}{n + 1}
     \]
   - 假设“失败端支配”（Failure-side dominance）：在不可行任务上，在线得分的分布不会比参考池的右尾更重。

3. **证据累积（E-process Accumulation）**  
   - 采用 **e-process（始终有效统计过程）** 累积校准后的证据值：
     \[
     E_t = \prod_{s=1}^t f_s(p_s)
     \]
     其中 \(f_s(\cdot)\) 是非增、积分不超过1的 Betting 函数（例如截断幂函数）。
   - 当累积证据超出阈值 \(E_t \ge 1/\alpha\) 时发布结果，否则继续。

4. **发布判定**  
   - 定义发布时刻：\(\tau_\alpha = \inf \{t \ge 1 : E_t \ge 1/\alpha\}\)。  
   - 若在最大迭代步 \(T_{max}\) 内未达到阈值则“弃权”不发布。  

### 2.3 理论性质

- **安全性保证**：在假设1下，始终满足 \(P(D=1|F=0) \leq \alpha\)，即错误发布受控。
- **有效性分析**：在可行任务上，只要积累的正确候选贡献足够的“校准增益” \(B_T\)，即可保证以指数速率达到发布决定。  
- **稳健性**：如果校准分布随时间产生漂移（Calibration Drift），错误发布概率仍以有限偏差增长（\(\alpha(1+M\epsilon)^T\))）。

## 3. 实验设计

### 3.1 数据集与场景

- **基准数据集**：MBPP+（Mostly Basic Python Problems Plus），是一种用于代码生成的标准测试集。
- **场景定义**：LLM 编码代理在每个编程任务上生成最多 10 个候选程序；在线验证器仅评估一部分“可见测试”，而真正的正确性由隐藏测试集合决定。
- **可行任务与不可行任务划分**：  
  - 可行任务 \(F_1\)：存在至少一个通过隐藏测试的正确程序。  
  - 不可行任务 \(F_0\)：所有候选均错误。

### 3.2 比较方法（Baselines）

- **First_p**：单步p值阈值判定（不累积证据）。
- **Entropy**：基于概率熵的信心提前停止策略。
- **Stability**：基于连续得分稳定性的停止策略。
- **Ours**：提出的始终有效发布封装器（累积e-process）。

### 3.3 指标与分析

- 对比指标：
  - 错误发布率 \(P(D=1|F=0)\)
  - 可行任务释放率 \(P(D=1|F=1)\)
  - 发布后失败率 \(P(Y_\tau=0|D=1)\)
  - 平均发布步数

- **实验维度**：
  - 不同显著性阈值（α ∈ {0.20, 0.10, 0.05})
  - 不同参考池上限比例（top35–top85）
  - 不同可见测试数量 \(N_{test} ∈ {10, 20, 30}\)
  - 不同 betting 函数参数 η ∈ {0.3, 0.5, 0.7, 0.9}

## 6. 主要结论与发现

1. **安全性**：始终控制错误发布率在预设阈值 α 以下。
