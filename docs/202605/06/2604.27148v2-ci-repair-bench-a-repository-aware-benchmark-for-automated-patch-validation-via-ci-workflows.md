## 摘要
持续集成（Continuous Integration，CI）通过多阶段工作流在仓库级别上强制实现正确性，是现代软件开发的核心环节。然而，诊断和修复 CI 失败仍然充满挑战。与传统的程序修复不同，CI 失败往往涉及非代码工件、环境与依赖问题、噪声执行日志以及工作流级别的约束。现有的程序修复基准在这一场景下表现不足：它们大多以测试为中心，将修复限制在源代码层面，假设执行环境固定，并在简化的 CI 工作流中进行评估，无法反映真实的仓库级验证过程。我们提出了 CI-Repair-Bench —— 一个面向 CI 验证的、仓库级的程序修复基准集，构建自实际的 GitHub Actions 执行结果。该基准包含来自 103 个仓库的 567 个 CI 失败实例，修复正确性的评估完全基于在原始工作流下的完整 CI 重新执行。失败被划分为 12 种 CI 错误类型，从而实现基于错误类型的细粒度评估。为了展示基准的使用方法，我们提供了一个参考 CI 修复工作流，用于分析 CI 日志、定位故障并生成候选补丁。实证结果表明，自动修复在格式化和 linter 等可局部化、受工具控制的失败中最为有效，而环境、依赖及配置相关的失败依然具有挑战性；表现最好的大语言模型（LLM）实现了 18.9% 的修复成功率。CI-Repair-Bench 为推动 CI 原生自动程序修复研究提供了一个现实的评估基础。

## Abstract
Continuous Integration (CI) enforces repository-level correctness through multi-stage workflows and is central to modern software development, yet diagnosing and repairing CI failures remains challenging. Unlike traditional program repair, CI failures frequently involve non-code artifacts, environment and dependency issues, noisy execution logs, and workflow-level constraints. Existing program repair benchmarks fall short in this setting: they are largely test-centric, restrict repairs to source code, assume fixed execution environments, and evaluate under simplified CI workflows that do not reflect real repository-level validation. We introduce CI-Repair-Bench, a benchmark for CI-verified, repository-level program repair constructed from real GitHub Actions executions. It contains 567 CI failure instances from 103 repositories and evaluates repair correctness exclusively through full CI re-execution under original workflows. Failures are categorized into 12 CI error types, enabling fine-grained, error-type-aware evaluation. To demonstrate benchmark usage, we include a reference CI repair workflow that analyzes CI logs to localize faults and generate candidate patches. Empirical results show that automated repair is most effective for localized, tool-enforced failures such as formatting and linting, while environment, dependency, and configuration-related failures remain challenging; the best-performing LLM achieves an 18.9% repair success rate. CI-Repair-Bench provides a realistic evaluation foundation for advancing research on CI-native automated program repair.

## 一、研究背景与核心问题

- **研究动机**  
  现代软件开发普遍依赖持续集成（Continuous Integration, CI）机制，以保证在频繁代码提交中仓库级别的一致性与可构建性。  
  然而，**CI 失败的诊断与修复**极为复杂：其原因可能来自环境差异、依赖冲突、配置错误、脚本失效等多因素，而非简单的源代码缺陷。  
  现有自动程序修复（Automated Program Repair, APR）基准（如 Defects4J、SWE-bench 等）主要：
  - 聚焦单文件或单点代码错误；
  - 使用测试通过/失败作为唯一验证标准；
  - 在固定容器环境下执行。  

  因此，这些基准缺乏对“**真实CI上下文下的仓库级修复**”的评估能力。

- **研究目标**  
  作者提出一个新型的 **CI 级自动修复评测体系** —— **CI-Repair-Bench**，旨在：
  1. 真实重现 CI 环境的完整工作流；
  2. 支持源代码与非代码工件（如配置、依赖文件、工作流定义）修复；
  3. 通过 **重新执行原始 CI 流程** 验证修复的正确性；
  4. 为 LLM 等模型提供一个更贴近现实的修复任务与可解释评估框架。

## 二、核心方法与技术框架

### 1. CI-Repair-Bench 的总体构建流程

基准建设采用自动化流水线（共五阶段）从 **真实 GitHub Actions 数据**中提取可重放的 CI 失败实例：

1. **仓库筛选**：选择 103 个活跃的开源 Python 项目（≥1000 stars & forks，最近90天活跃）。
2. **CI 运行历史挖掘**：提取“失败–成功”配对提交（Fail-to-Pass Pairs），确保同一工作流下可比。
3. **数据清洗与标准化**：
   - 剔除部署类、文档生成类及不可复现的工作流；
   - 对 CI YAML 文件去冗余，仅保留验证相关阶段；
   - 维持语义等价性（通过 re-run 验证）。  
4. **最小修复差异提取**：
   - 基于失败日志、变更文件及验证步骤，提取“最小修补片段”；
   - 经完整 CI 重执行确认确实可恢复成功；
   - 得到“**经验证的 Ground-truth Patch**”。  
5. **实例组装与标注**：
   - 每个样本包含：仓库元数据+CI 配置+失败日志+修复补丁；
   - 同时标注 1–N 个错误类型（共 12 类，如依赖、格式化、语法、配置等）。

最终形成 **567 个实例、893 个错误标签**。

### 2. 评估机制与核心思想

- **评价指标：**
  - **Pass@1（主指标）**：单次修复尝试后，CI 从 fail→pass 的比例。
  - **Per-Error-Type Accuracy**：按错误类型细分成功率。

- **验证方式：**
  - 在原始 CI 工作流中重新执行补丁版本；
  - 所有任务必须在 GitHub Actions 上“全任务通过”才算修复成功；
  - 覆盖环境配置、依赖解析、构建、格式校验、测试执行等多阶段。

---

### 3. 参考修复框架（Reference CI Repair Framework）

论文还实现了一个 **基于 LLM 的三阶段自动修复流水线**，用于展示如何结合日志、代码与上下文执行修复：

#### （1）CI 日志分析（Log Analysis）
- **挑战**：CI 日志噪声大、长度超出上下文限制。  
- **策略**：
  - 基于 Token 分片（chunking），并优先保留出现错误的末段；
  - 使用 **Agent-based 迭代推理** （采用 LLM 分步总结日志片段形成结构化“失败摘要”）；
  - 与 **BM25 检索式策略** 对比（仅基于关键词匹配）。

#### （2）故障定位（Fault Localization）
- **三级定位流程**：
  1. **基于改动选择候选文件**（使用最近修改历史）；
  2. **LLM 文件筛选**（验证文件与失败摘要之间的因果关联）；
  3. **细粒度定位**（函数或代码块级别，输出行范围和错误类别）。
  
- 输出结构化的定位报告（JSON对象，包含行号、原因、故障级别）。

#### （3）补丁生成（Patch Generation）
- **优先工具修复**：若错误类型匹配已有工具（如 `ruff`、`black`），则生成命令实现自动修复；
- **其次LLM直接生成代码编辑**：依据定位信息最小修改；
- 最后经三方合并（3-way merge）形成可应用补丁；
- 在 CI 原环境中 **直接复跑验证修复成功与否**。

## 六、主要结论与发现

1. **总体修复成功率较低但显著**：  
   - GPT-5-mini 在全流程 CI 验证下达 **18.9% Pass@1**；
   - 其他模型在 7.9%–15.9% 之间。
2. **日志分析策略影响显著**：  
   - 替换为 BM25 检索后，Pass@1 降低 28%–75.9%；  
   - 说明 **迭代型 LLM 理解日志** 对性能至关重要。
3. **错误类型修复难度分层**：
   - 上层：格式化（35.5%）、lint错误（17.8%）；  
   - 中层：测试、语法、运行时错误（≈10–13%）；  
   - 底层：依赖、配置、环境问题（<9%，部分为0%）。
4. **修复成功与“错误信号局部性”正相关**：  
   明确指出位置的错误（如格式规则）更易自动修复，而跨文件或依赖驱动的错误仍难解决。
5. **资源消耗权衡**：  
   Agent模式虽成本高约5倍，但修复率与定位精度明显更优。

## 八、不足与局限

- **数据覆盖性有限**：仅涵盖 Python 语言及 GitHub Actions 平台；
- **CI 可重放性问题**：受外部依赖版本更新或 runner 变动影响；
- **Ground-truth patch 可能非唯一**：仅保留“最小可通过补丁”，可能非唯一真实修复；
- **CI 日志可见性受限**：fail-fast 模型导致部分后续错误未暴露；
- **LLM 推理具随机性**：同输入仍可能不同输出，影响结果稳定；
- **高资源成本**：Agent-based 推理在大规模实验上成本高昂；
- **尚缺跨语言、跨平台验证**：外推到 Java/C++/其他 CI 系统需再验证。
