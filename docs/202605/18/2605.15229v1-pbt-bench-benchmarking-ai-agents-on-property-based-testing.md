## 摘要
现有的代码基准测试通常衡量智能体是否能生成能重现已知错误的测试，或能否生成修复所描述问题的补丁。这两种方式都无法单独评估基于性质测试的独特能力：从文档中推导语义不变量，并构建足够精确的输入生成策略，使随机搜索能揭示违反该不变量的情况。我们提出了 PBT-Bench，这是一个涵盖 40 个真实 Python 库的 100 个精心设计的基于性质测试问题的基准数据集。每个问题注入一个或多个语义缺陷（共 365 个，平均每题 3.65 个），这些缺陷设计成默认随机策略几乎无法触发；智能体必须阅读库文档，识别相关不变量，并指定一个能将采样集中在触发区域的 Hypothesis @given 策略。缺陷按三种难度等级（L1-L3）分层，范围从单约束边界缺陷到涉及状态和跨函数协议违反的问题。我们在两种提示方案（开放式基线与显式 Hypothesis 支架）下，对八个当代大型语言模型进行了评估，每种配置独立运行三次。在 PBT 引导的提示下，缺陷召回率在不同模型间介于 42.1% 至 83.4%；在开放式基线下，介于 31.4% 至 76.7%。Hypothesis 支架可使中等能力模型的性能提升超过 20 个百分点，但对最强模型提升较小，且有两个模型出现性能下降，表明结构化提示可能与某些模型的内部机制冲突而非相辅相成。最难的缺陷呈现模型特定性：不同架构模型在不同问题上失败，导致没有单一模型能覆盖所有问题。我们公开该基准、评测框架及完整评估语料，以支持后续基于文档的语义推理研究。

## Abstract
Existing code benchmarks measure whether an agent can produce any test that reproduces a known bug, or whether it can produce a   patch that fixes a described issue. Neither isolates the distinct skill of property-based testing: deriving a semantic invariant   from documentation, and then constructing an input-generation strategy precise enough to make a random search reveal the violation.   We introduce PBT-Bench, a benchmark of 100 curated property-based testing problems across 40 real Python libraries. Each problem   injects one or more semantic bugs (365 in total, mean 3.65 per problem) designed so that default-strategy random inputs almost   never trigger them; the agent must read the library's documentation, identify the relevant invariant, and specify a Hypothesis   @given strategy that concentrates mass in the trigger region. Bugs are stratified across three difficulty levels (L1-L3) spanning   single-constraint boundary bugs to stateful, cross-function protocol violations. We evaluate eight contemporary LLMs under two   prompting regimes (open-ended baseline vs. explicit Hypothesis scaffolding) for three independent runs per configuration. Bug   recall under the PBT-guided prompt ranges from 42.1% to 83.4% across models; under the open-ended baseline, from 31.4% to 76.7%.   Hypothesis scaffolding lifts mid-capability models by over 20 percentage points, but yields smaller gains for the strongest models,   with two exceptions showing degradation, suggesting the structured prompt can interfere with certain model behaviours rather than   complementing them. The hardest bugs prove model-specific: different architectures fail on different problems, leaving persistent   gaps that no single model closes. We release the benchmark, harness, and full evaluation corpus to support downstream work on   documentation-grounded semantic reasoning.

## 一、研究背景与核心问题

- **研究动机**：现有代码智能体评价体系（如 SWE-Bench、SWT-Bench）偏重于「是否能复现或修复错误」，但无法衡量一个智能体推理程序“语义不变量”的能力。  
- **问题本质**：在文档指定的抽象语义约束下，如何让模型**自动推导属性 (property)** 并生成输入策略，让随机测试揭示违反该属性的情况。  
- **研究目标**：评估 AI 模型能否执行「基于性质测试（Property-Based Testing, PBT）」——从文档语义抽象出性质、构造输入生成策略、并找出语义层面的漏洞。

---

## 二、方法论与技术路线

### 1. 核心思想
- 通过评估模型执行 PBT 的能力，单独测量模型的“**语义推理 + 随机输入设计**”能力。
- PBT 的核心包括两部分：
  1. **不变量识别**：从库文档推导在所有输入上应保持的语义性质；
  2. **输入策略生成**：利用 Hypothesis 框架的 `@given` 装饰器和复合策略生成具代表性的输入样本。
- 目标是让模型自动生成能使错误显露的输入分布。

### 2. Benchmark 构建
- **PBT-Bench** 基准包含：
  - 100 个经过人工策划的问题；
  - 来自 40 个真实的 Python 库；
  - 共计 365 个注入语义 bug（平均每问题 3.65 个）。
- 每个问题配有：
  - 可反转的补丁；
  - 对应文档（唯一信息来源）；
  - Ground truth 策略；
  - 难度分级 L1–L3（从单约束到跨函数协议级 bug）。

### 3. 技术细节
- **评测框架**：
  - 使用双容器评测结构：  
    - *agent container*：运行模型编写测试。  
    - *eval container*：对每个 bug 独立应用 F→P（Fail-on-buggy, Pass-on-fixed）验证。
- **输入策略验证标准**：bug 可触发于确定的输入区域（概率为 1），避免随机偶然性。
- **难度定义**：
  - L1：单约束或边界条件；
  - L2：多约束组合；
  - L3：状态或跨函数协议错误。
- **Prompt 设计**：
  - *Baseline*：开放式指令生成常规测试，未涉及 Hypothesis；
  - *PBT*：结构化提示，明确要求 `@given`、属性分类表（Roundtrip/Invariant/Model-Oracle）。

## 三、实验设计与对比评测

### 1. 数据与模型
- 使用 **PBT-Bench** 自建数据集；涵盖序列化、数据结构、日期时间、数值计算、解析等七大类库。
- 对比 **八个当代大型语言模型**：
  - Claude Sonnet 4.6  
  - DeepSeek V3.2  
  - Gemini 3 Flash  
  - GLM 5.1  
  - Grok 4.1 Fast  
  - Qwen 3.6 Plus  
  - Qwen 3.5-30B-A3B  
  - Step 3.5 Flash

### 2. 实验设置
- 每个模型分别在两种提示模式下进行测试（Baseline vs. PBT）。
- 每种配置运行三次，共 **4,800 条模型运行轨迹**。
- 每次运行上限：200 次工具调用、60 分钟时限。
- 确保文档是唯一知识来源，不允许模型读取源码。

### 3. 评估指标
- **Bug Recall**：找到的 bug 数 / 总 bug 数。
- **覆盖率 (F≥1)**：至少发现一个 bug 的问题比例。
- **完全召回率**：所有 bug 均被检测的问题比例。
- **测试精度**：有效测试数 / 生成测试总数。

### 4. 对照基线
- 与多种现有测试基准类比（SWE-Bench、SWT-Bench、TestExplora），但这些都不直接考察 PBT 能力，本基准为首个专门设计的 PBT 测试。

## 六、主要成果与发现

### 1. 总体性能
- Bug召回率范围：
  - Baseline：31.4%–76.7%
  - PBT 模式：42.1%–83.4%
- PBT 提示可平均提升约 **20–25 个百分点**，尤其增强中等能力模型表现。

### 2. 模型差异
- 最强模型（Sonnet 4.6）在 PBT 模式下召回率最高（83.4%）。
- 弱势模型（如 Qwen 3.5-30B-A3B、Step 3.5 Flash）提升最大（+22% 以上）。
- 两个模型出现负提升（DeepSeek V3.2、Grok 4.1 Fast），说明过度结构化提示可能干扰模型自主搜索。

### 3. 组合分析
- 所有模型模式联合（16 个单元）可覆盖 99.5% 的 bug。
- 单模型 + 双模式组合即可显著增益（同一模型的两种提示互补性高达 65%）。

### 4. 难度与失败模式
- 难度与召回率呈明显负相关（L1 > L2 > L3）。
- 常见失败类型：
  - Baseline：错误断言、过于具体的输入；
  - PBT 模式：误用 `assume()` 导致排除触发区，或策略范围错误。
- 提出改进建议：在 PBT 提示中显式警告“不要过滤可疑输入”。

## 七、方法与实验亮点

- **系统化的基准设计**：首个针对属性测试能力而非修复能力的 benchmark。
- **精细 QA 与可复现性**：三层验证；容器化环境确保 F→P 评分一致。
- **文档驱动测试生成**：让模型从自然语言文档推导不变量，体现真正的语义理解。
- **跨模型对比公平性**：统一 SDK（OpenHands）、统一超参数与时间上限。
- **丰富分析**：包含故障分类、难度梯度验证、prompt 敏感性分析、交叉模型互补性探索。

## 八、不足与局限

- **分布代表性**：注入 bug 虽严格控制语义特性，但不完全代表真实代码生态分布。
- **语言与平台限制**：仅涵盖 Python 与英文文档，其他语言和多语文档未测试。
- **搜索预算固定**：Hypothesis 默认 `max_examples = 200` 可能限制复杂 L3 bug 的发现。
- **环境约束**：仅使用单一 SDK 与有限工具集；更复杂的编程环境可能显著影响表现。
- **Prompt 敏感性未充分探索**：虽然有版本变体测试，但缺乏系统性的多模型多变体分析。
