## 摘要
持续集成（CI）通过多阶段工作流在仓库级别上强制代码正确性，是现代软件开发的核心。然而，诊断和修复CI故障仍然具有挑战性。与传统的程序修复不同，CI故障常常涉及非代码工件、环境与依赖问题、嘈杂的执行日志以及工作流级约束。现有的程序修复基准在此情境下表现不足：它们主要以测试为中心，将修复限制在源代码层面，假设固定的执行环境，并在简化的CI工作流下进行评估，这并不能反映真实的仓库级验证。我们提出了CI-Repair-Bench，一个基于CI验证、仓库级的程序修复基准，构建自真实的GitHub Actions执行数据。它包含来自103个仓库的567个CI故障实例，并通过原始工作流下的完整CI重新执行来评估修复正确性。故障被划分为12种CI错误类型，可实现细粒度、基于错误类型的评估。为了展示基准的使用，我们提供了一个参考CI修复工作流，用于分析CI日志、定位故障并生成候选补丁。实证结果表明，自动修复对局部化、由工具强制执行的故障（如格式和lint错误）最为有效，而环境、依赖及配置相关的故障仍然具有挑战；表现最佳的LLM达到了18.9%的修复成功率。CI-Repair-Bench为推动CI原生自动程序修复研究提供了一个现实的评估基础。

## Abstract
Continuous Integration (CI) enforces repository-level correctness through multi-stage workflows and is central to modern software development, yet diagnosing and repairing CI failures remains challenging. Unlike traditional program repair, CI failures frequently involve non-code artifacts, environment and dependency issues, noisy execution logs, and workflow-level constraints. Existing program repair benchmarks fall short in this setting: they are largely test-centric, restrict repairs to source code, assume fixed execution environments, and evaluate under simplified CI workflows that do not reflect real repository-level validation. We introduce CI-Repair-Bench, a benchmark for CI-verified, repository-level program repair constructed from real GitHub Actions executions. It contains 567 CI failure instances from 103 repositories and evaluates repair correctness exclusively through full CI re-execution under original workflows. Failures are categorized into 12 CI error types, enabling fine-grained, error-type-aware evaluation. To demonstrate benchmark usage, we include a reference CI repair workflow that analyzes CI logs to localize faults and generate candidate patches. Empirical results show that automated repair is most effective for localized, tool-enforced failures such as formatting and linting, while environment, dependency, and configuration-related failures remain challenging; the best-performing LLM achieves an 18.9% repair success rate. CI-Repair-Bench provides a realistic evaluation foundation for advancing research on CI-native automated program repair.

- **核心问题**

## 二、方法论与技术路线

- **核心思想**  
  构建一个名为 **CI-Repair-Bench** 的真实CI故障评测基准。它基于从 GitHub Actions 获取的实际CI失败数据，通过重新执行完整CI工作流来验证每个修复补丁是否真正有效。

- **关键技术设计**
  1. **仓库级数据收集**：从 103 个 Python 仓库中提取 567 个真实 CI 失败–成功（fail/pass）提交对。每个实例包含：
     - 仓库元数据（repo名称、分支）
     - 相应CI工作流配置文件（workflow YAML）
     - 失败执行日志
     - 成功提交的最小修复补丁（ground truth patch）
  2. **错误类型标注**：基于日志和提交内容定义 12 种 CI 错误类型（格式、lint、测试、依赖、环境、配置等）。
  3. **评估标准**：不以单元测试为验证标准，而是以 **完整CI工作流再次执行的成功（Pass@1）** 为补丁有效性判断依据。
  4. **参考修复框架**：提出三阶段自动修复流程：
     - *CI日志分析（Log Analysis）*：使用LLM分块分析长日志，提取失败关键信息；
     - *故障定位（Fault Localization）*：识别受影响的文件和具体代码行；
     - *补丁生成（Patch Generation）*：结合CI上下文生成局部、可执行的代码修改，从而通过CI验证。
  5. **LLM驱动修复实现**：参考框架通过四种语言模型（GPT-5-mini、GPT-4o-mini、DeepSeek-Coder、DeepSeek-Chat）进行评估。

- **评估指标**
  - Repair Success Rate（成功修复率）= 成功运行CI的样本比例。
  - Per-error-type Accuracy（按错误类型统计的修复准确率）。
  - Top-k Localization 和 MAP（平均排名精度），用于评估故障诊断质量。

## 三、实验设计与评测基准

- **Benchmark 数据集**  
  - 数据源：真实的 GitHub Actions 执行日志与对应仓库提交历史。  
  - 规模：567 个 CI 失败实例，覆盖 12 种错误类别，来自 103 个活跃的 Python 仓库。
  - 对比对象：与其他 APR 基准如 SWE-bench、FEA-Bench、GitBug-Actions 等进行结构性比较，CI-Repair-Bench 是唯一支持仓库级工作流重执行验证的基准。

- **实验流程**  
  1. 对所有 567 个实例应用参考修复框架；
  2. 分别采用四种 LLM 作为核心修复引擎；
  3. 比较不同日志分析策略（Agent-based vs. Retrieval-based）对修复效果的影响；
  4. 按错误类型统计修复率差异。

- **对比方法**
  - 主要对比两种日志解析策略：
    - Agent-based（迭代推理式）
    - Retrieval-based（BM25检索式轻量分析）
  - 同时比较不同模型的修复、定位能力。

## 六、主要结论与发现

1. **总体性能**
   - 最优模型（GPT-5-mini）在完整CI重执行验证下修复成功率仅 **18.9%**。
   - 其他模型在 7.9%–15.9% 范围内。

2. **日志分析影响**
   - Agent-based策略比Retrieval-based高出28%–75%的修复成功率；
   - 尽管资源消耗更高，但迭代推理能显著提升故障定位与补丁质量。

3. **错误类型分布**
   - 高修复率类别：格式化（35.5%）、Lint（17.8%）；
   - 中等：测试、运行时、语法错误（约10%–13%）；
   - 低至几乎无修复：配置、环境、包安装类（0%–9%）。

4. **总体结论**
   - 当前LLM可处理显式、位置清晰的错误（如格式与lint），但缺乏对环境与依赖的跨文件推理。
   - CI-Repair-Bench揭示了当前自动修复在**环境感知、仓库级交互性**方面的瓶颈。
