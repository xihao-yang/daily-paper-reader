## 摘要
静态应用安全测试工具帮助开发者在发布前发现安全漏洞，但它们常常产生大量误报。这增加了人工审核的工作量，降低了开发者的信任度，并可能导致真实漏洞在噪声报告中被忽略。我们提出了 QASecClaw，一种多智能体方法，将传统的静态应用安全测试与基于大型语言模型的上下文代码审查相结合。SAST 引擎首先报告候选漏洞，随后由基于大型语言模型的 SAST 过滤智能体结合源代码上下文审查每个发现，以判断其更可能是真实还是误报。QASecClaw 由任务协调器进行整体调度，并包含用于测试规划、安全验证、证据关联、过滤和报告的专用智能体。我们在 OWASP Benchmark v1.2 上评估了 QASecClaw，该基准包含 11 类共同弱点枚举（CWE）类别的 2,740 个 Java 测试用例及真实标签。QASecClaw 实现了 90.93% 的 F1 分数，而单独的 Semgrep 仅为 78.39%。这一提升主要来自误报减少 88.6%，由 560 降至 64，同时召回率仅降低 3.1%。这些结果表明，结合大型语言模型的多智能体验证可以使静态应用安全测试的输出更加准确、有用且值得信赖。

## Abstract
Static Application Security Testing tools help developers find security vulnerabilities before release, but they often produce many false positives. This increases manual review effort, reduces developer trust, and may cause real vulnerabilities to be ignored among noisy reports. We present QASecClaw, a multi agent approach that combines conventional Static Application Security Testing with coding specialized Large Language Model based contextual code review. A SAST engine first reports candidate vulnerabilities, and a Large Language Model based SAST Filter Agent then reviews each finding with source code context to decide whether it is likely to be a true positive or a false positive. QASecClaw is coordinated by a Mission Orchestrator and includes specialized agents for test planning, security validation, evidence correlation, filtering, and reporting. We evaluate QASecClaw on OWASP Benchmark v1.2, which contains 2,740 Java test cases across 11 Common Weakness Enumeration categories with ground truth labels. QASecClaw achieves an F1 score of 90.93 percent, compared with 78.39 percent for standalone Semgrep. The improvement is mainly driven by an 88.6 percent reduction in false positives, from 560 to 64, with only a 3.1 percent reduction in recall. These results show that Large Language Model augmented multi agent verification can make Static Application Security Testing output more accurate, useful, and trustworthy.

## 一、研究背景与核心问题

- **研究动机**  
  静态应用安全测试（Static Application Security Testing，SAST）是软件开发流程中用于检测源代码潜在安全漏洞的重要环节。它在不执行程序的情况下分析代码，可提前发现风险并防止漏洞进入生产环境。  
  然而，实际使用中 SAST 工具（如 Semgrep、SonarQube、Fortify 等）常因保守策略而产生大量**误报（False Positives）**，即错误地标记安全代码为漏洞。这导致：
  - 开发者必须花费大量人工审查时间；
  - 过多的错误警告降低了工具的可信度；
  - 真漏洞可能被忽略、导致安全隐患。
  
- **研究目的**  
  本论文旨在提出一种能够**显著降低 SAST 误报率**的自动化方法，使安全测试结果更可靠、实用，并提升开发者的信任度。

## 二、方法论与技术细节

### 1. 核心思想
- 保留传统 SAST 的**高召回（High Recall）**特点；
- 引入**大语言模型（LLM）作为上下文代码审查者**，仅对 SAST 工具的候选漏洞结果进行验证；
- 采用**多智能体框架**执行任务分解与协调，将分析过程划分为多个专用角色（Agent）。

### 2. 系统结构
QASecClaw 的整体架构由五个核心智能体组成，并由“任务协调器（Mission Orchestrator）”统一控制：
1. **测试规划智能体（Test Planning Agent）**：负责准备目标代码与任务流。
2. **安全验证智能体（Security Validation Agent）**：调用 Semgrep 进行初步 SAST 扫描。
3. **证据关联智能体（Evidence Correlation Agent）**：判断是否存在动态证据（如日志或运行轨迹），有则直接验证为真阳性。
4. **SAST 过滤智能体（SAST Filter Agent）**：核心模块，利用 LLM 对每个未验证发现进行上下文分析。
5. **报告生成智能体（Report Generation Agent）**：整合最终结果，输出经验证的漏洞报告。

### 3. LLM 审查机制（SAST Filter Agent）
- 处理流程：
  1. 将候选漏洞文件分批（每批 15 个）读取；
  2. 构建**基于 CWE 分类的上下文提示词（prompt）**；
  3. 调用编码专用 LLM（Qwen 3.5 Plus），判定“是否真实漏洞”；
  4. 验证 LLM 返回的结构化 JSON 输出；
  5. 若响应异常（如超时或格式错误），采用**“Fail-Open”策略**保留整批结果，避免误删真实漏洞。
  
- 式化度量（用于评估）：
  - Precision = TP / (TP + FP)
  - Recall = TP / (TP + FN)
  - F1 = 2 × Precision × Recall / (Precision + Recall)
  - FPR = FP / (FP + TN)
  - Youden’s J = TPR − FPR（用于整合识别与误报率）
