## 摘要
近期的大语言模型（LLMs）在标准基准测试上的自动程序修复任务中表现出强劲性能。然而，这些基准仅在单一规范形式的缺陷代码上评估模型，未能反映真实软件中常见的语法变体，从而使鲁棒性问题基本未被检验。在本文中，我们构建了 HEJ-Robust —— 一个基于 HumanEval-Java-Bug 构建的鲁棒性基准，通过八种保持语义不变的代码变换生成了 1,450 个转换实例。我们在该基准上评估了五个经过微调的大语言模型，结果显示在多种变换下模型性能下降超过 50%，这表明当前基于 LLM 的修复模型对轻微语法变动缺乏鲁棒性。

## Abstract
Recent Large Language Models (LLMs) have shown strong performance on automated program repair across standard benchmarks. However, these benchmarks evaluate models on a single canonical form of buggy code and do not reflect the syntactic variations commonly observed in real-world software, leaving robustness largely unexamined. In this work, we construct HEJ-Robust, a robustness benchmark built from HumanEval-Java-Bug using eight semantics-preserving code transformations, resulting in 1,450 transformed instances. We evaluate five fine-tuned LLMs on this benchmark and show that model performance drops by over 50% under several transformations, indicating that current LLM-based repair models lack robustness to minor syntactic variations.

## 1. 核心问题与研究背景

- **研究动机**：近年来，大语言模型（LLMs）在自动程序修复（Automated Program Repair, APR）任务上表现优异。然而，主流 APR 基准（如 *Defects4J*、*HumanEval-Java-Bug*）仅评估模型在**单一语法形式**下的性能。现实软件中存在大量**语义等价但语法不同**的代码变体，当前评测无法反映模型在此类变化下的稳健性（robustness）。
- **核心问题**：现有 LLM 修复系统在面对语义保持但语法结构有所变化的代码时，是否依然能产生正确修复？缺乏系统化评估框架。
- **研究目标**：构建一个用于量化程序修复鲁棒性的标准化基准 **HEJ-Robust**，并系统评估 LLM 模型在语法变体场景下的性能衰减。

## 2. 方法论与技术方案

### 2.1 核心思想
- 在现有 *HumanEval-Java-Bug* 基准的基础上，通过**八种语义保持（semantics-preserving）代码变换**生成大量具有真实变体特征的测试实例，以测试 LLM 修复过程的稳健性。
- 这些变换不改变代码逻辑或测试输出，只在语法层引入扰动，从而检查模型是否过度依赖表层代码模式。

### 2.2 八种语义保持变换
| 类型 | 描述 | 示例 |
|------|------|------|
| 1. 局部变量重命名 | 随机但自然地更改变量名 | `int temp=0;`→`int count=0;` |
| 2. 方法重命名 | 修改函数名但保持逻辑 | `int compute()`→`int calculate()` |
| 3. 参数重命名 | 修改形参命名 | `void foo(int x)`→`void foo(int val)` |
| 4. 插入日志语句 | 在函数开头插入 `System.out.println("log");` |
| 5. 插入 try-catch 块 | 在安全位置添加异常处理 |
| 6. 布尔值交换 | 反转初始化并在使用处取反 | `res=true;`→`res=false; return !(res);` |
| 7. 循环交换 | 将 for 与 while 结构互换 |
| 8. 条件交换 | 交换判断条件两侧操作数 `if(a==b)`→`if(b==a)` |

### 2.3 技术管线与实现细节
- **AST 级实现**：基于 `JavaTransformer` 和 `JavaParser` 对程序 AST 进行可靠修改。
- **语义一致性保障**：  
  - 采用 *tree-sitter* 确保替换变量的语法一致性。  
  - 使用 *CodeBERT* 与 *GraphCodeBERT* 计算嵌入相似度，以生成语义自然的重命名结果。  
- **人工校验与重新标注**：所有变换后样本手动重新标定 bug 位置，以避免 buggy 行被变换破坏的情况。
- **评测指标**：  
  - **主要指标**：`Pass@10`（至少一条修复补丁通过全部测试）。  
  - **辅助指标**：`CodeBLEU`（代码相似性指标，不用于最终鲁棒性结论）。

  - **Pass@10**：以执行正确性（通过所有单元测试）为准；
  - **CodeBLEU**：仅作参考，不决定鲁棒性结论。

## 6. 主要结论与发现

- **显著脆弱性**：
  - 多数模型在轻微语法变动下性能大幅下降；
  - **变量重命名**使 Pass@10 降低约 **50–57%**；
  - **循环交换、插入 try-catch** 等结构变换也造成明显衰减。
- **无稳健性优势的大模型**：
  - 模型规模增大并未带来额外鲁棒性；
  - 在多种场景下，CodeT5-large 与 PLBART-large 反而下降更明显。
- **指标分歧**：
  - CodeBLEU 分数几乎保持稳定，说明代码表面相似并不代表功能正确；
  - 执行级指标更能反映鲁棒性问题。
- **总体结论**：
  当前 LLM 基于自动修复在面对语法等价变体时缺乏泛化能力，对轻微扰动极其敏感。
