## 摘要
大型语言模型（LLMs）加速了软件开发，但在非约束的工作流程中往往表现出不稳定性、非确定性，以及对开发规范的弱遵从性。尽管测试驱动开发（TDD）提供了结构化的红—绿—重构过程，现有的基于LLM的方法通常将测试作为辅助输入，而非可强制执行的流程约束。我们提出了一个AI原生的TDD框架，将经典的TDD原则操作化为结构化的提示级和工作流级治理机制。提取出的原则被形式化为机器可读的宣言，并分布于规划、生成、修复和验证阶段，形成分层架构，以区分模型提案与确定性引擎的权威。该系统通过强制阶段顺序、限定修复循环、验证闸门和原子性变更控制来提升稳定性与可复现性。我们描述了该架构，并讨论了如何将软件工程规范直接编码到提示编排中，我们认为这为可靠的LLM辅助开发提供了有前景的方向。

## Abstract
Large language models (LLMs) accelerate software development but often exhibit instability, non-determinism, and weak adherence to development discipline in unconstrained workflows. While test-driven development (TDD) provides a structured Red-Green-Refactor process, existing LLM-based approaches typically use tests as auxiliary inputs rather than enforceable process constraints. We present an AI-native TDD framework that operationalizes classical TDD principles as structured prompt-level and workflow-level governance mechanisms. Extracted principles are formalized in a machine-readable manifesto and distributed across planning, generation, repair, and validation stages within a layered architecture that separates model proposal from deterministic engine authority. The system enforces phase ordering, bounded repair loops, validation gates, and atomic mutation control to improve stability and reproducibility. We describe architecture and discuss encoding software engineering discipline directly into prompt orchestration, which we think offers a promising direction for reliable LLM-assisted development.

## 一、研究动机与背景

- **核心问题**：大型语言模型（LLMs）已成为软件开发中的重要工具，但其在非约束环境下存在明显的**不稳定性、非确定性和规范性缺失**。即使使用相同的提示和温度，生成的代码结果也常常不同，导致难以复现和验证。
- **研究动机**：传统测试驱动开发（Test-Driven Development，TDD）以“测试先行—实现通过—重构优化”的循环，确保代码质量与开发纪律。然而，现有的LLM代码生成流程虽然可生成测试，但无法像人类工程师那样**强制遵循TDD过程**。
- **研究目标**：作者希望创建一个**AI原生的TDD治理框架**，将TDD原则直接编码进LLM的提示与多智能体工作流，使其具备明确的阶段划分与执行约束，从而实现稳定、规范的自动化代码生成。

## 二、方法论

### 1. 核心思想

- 论文提出一种**“AI-native TDD Governance Framework”**，其目标是将人类软件工程中的TDD原则转化为**可机读、可执行的治理规范**。
- 核心理念是：  
  - 将 TDD 的“红—绿—重构”阶段作为强制约束嵌入到工作流中；  
  - 将每个阶段拆分为多个由不同智能体负责的提示角色（planner、generator、repairer、validator）；  
  - 通过一个引擎保持“执行权威”，而模型仅作为“提案生成者”。

### 2. 技术实现与流程

- **原则提取与形式化**：  
  - 通过对 Kent Beck 与 Robert C. Martin 的经典著作分析，提炼出四类可治理原则：**顺序约束、粒度控制、反馈质量、设计整洁性**。  
  - 将这些原则编码为 JSON 格式的“**TDD Manifesto（TDD宣言）**”，其中包含规则、禁止模式与执行约束。

- **架构层次划分**：  
  - **Planner（规划器）**：根据需求生成阶段任务与预期测试结果，确保测试先行（RED）。  
  - **Generator（代码生成器）**：仅在测试失败情况下生成最小实现（GREEN）。  
  - **Repairer（修复器）**：根据错误类别执行局部修复，限定三次循环（bounded repair）。  
  - **Validator（验证器）**：执行确定性测试与结构化审查，通过则进入下一阶段。  
  - **Governance Engine（治理引擎）**：拥有文件状态的唯一修改权限，确保所有变更原子执行与记录。

- **约束机制与算法逻辑**：  
  - **阶段顺序强制**：禁止在没有失败测试时直接生成代码。  
  - **验证闸门（Validation Gate）**：在每次提案前执行语义、结构和策略检查。  
  - **循环控制**：检测重复错误或无效补丁，触发早停或重启。  
  - **行为保持（Behavior Preservation）**：重构阶段要求完整回归测试，不允许引入新功能或修改测试。

- **提示分布策略**：各智能体的提示模板嵌入这些约束，从而在语言层和执行层都保持一致的开发纪律。
